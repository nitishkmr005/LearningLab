## Q1: What are the types of SQL commands (DDL, DML, DCL, TCL)?

SQL commands are grouped by what they do to the database:

| Category | Full Name | Commands | What It Does |
|---|---|---|---|
| **DDL** | Data Definition Language | CREATE, ALTER, DROP, TRUNCATE | Defines and changes the structure (schema) of tables |
| **DML** | Data Manipulation Language | SELECT, INSERT, UPDATE, DELETE | Reads and modifies the actual data |
| **DCL** | Data Control Language | GRANT, REVOKE | Controls who can access or modify data |
| **TCL** | Transaction Control Language | COMMIT, ROLLBACK, SAVEPOINT | Manages transactions — save or undo a group of changes |

**Example:**

```sql
-- DDL: define the structure
CREATE TABLE employees (id INT, name TEXT, salary FLOAT, dept TEXT);

-- DML: insert and read data
INSERT INTO employees VALUES (1, 'Alice', 90000, 'Eng');
SELECT * FROM employees;

-- TCL: undo a mistake safely
BEGIN;
DELETE FROM employees WHERE id = 1;
ROLLBACK;  -- Alice is restored
```

**Intuition:** DDL = designing the building (schema). DML = moving furniture (data). DCL = handing out key cards (access). TCL = saving your progress in a game (transactions).

## Q2: What is the SQL execution order?

SQL is written in one order but the database processes it in a different order. This is one of the most common sources of confusion — especially around why certain things fail.

**Written order (how you type it):**
```sql
SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
```

**Execution order (how the database actually processes it):**

| Step | Clause | What happens |
|---|---|---|
| 1 | **FROM** | Load the table |
| 2 | **JOIN** | Combine tables |
| 3 | **WHERE** | Filter individual rows (before grouping) |
| 4 | **GROUP BY** | Group the filtered rows |
| 5 | **HAVING** | Filter groups (after aggregation) |
| 6 | **SELECT** | Compute expressions and pick columns |
| 7 | **ORDER BY** | Sort the result |
| 8 | **LIMIT** | Trim to N rows |

**Why this matters — three common mistakes explained:**

```sql
-- MISTAKE 1: Using a SELECT alias in WHERE (WHERE runs before SELECT)
SELECT salary * 12 AS annual_salary
FROM employees
WHERE annual_salary > 100000;   -- ERROR: annual_salary doesn't exist yet at WHERE step

-- FIX: repeat the expression
WHERE salary * 12 > 100000;

-- MISTAKE 2: Using aggregate in WHERE (aggregation hasn't happened yet)
SELECT dept, COUNT(*) FROM employees
WHERE COUNT(*) > 5   -- ERROR: use HAVING instead
GROUP BY dept;

-- CORRECT: HAVING runs after GROUP BY
HAVING COUNT(*) > 5;

-- CORRECT: ORDER BY CAN use aliases (it runs after SELECT)
SELECT salary * 12 AS annual_salary
FROM employees
ORDER BY annual_salary DESC;   -- this works
```

## Q3: What are the types of JOINs? Explain each with an example.

A JOIN combines rows from two tables based on a matching column.

**Setup — two tables:**

`employees`:
| emp_id | name | dept_id |
|---|---|---|
| 1 | Alice | 10 |
| 2 | Bob | 20 |
| 3 | Carol | NULL |

`departments`:
| dept_id | dept_name |
|---|---|
| 10 | Engineering |
| 30 | Marketing |

---

**INNER JOIN** — Only rows that match in BOTH tables:
```sql
SELECT e.name, d.dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.dept_id;
```
Result: **Alice → Engineering** only. Bob (dept 20, no match) and Carol (NULL dept) are excluded. Marketing (dept 30, no employee) is also excluded.

---

**LEFT JOIN** — All rows from the LEFT table + matched rows from right (NULLs for no match):
```sql
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;
```
Result: Alice (Engineering), Bob (NULL), Carol (NULL). Every employee appears.

---

**RIGHT JOIN** — All rows from the RIGHT table + matched rows from left:
Result: Alice (Engineering), NULL (Marketing). Every department appears.

---

**FULL OUTER JOIN** — All rows from BOTH tables (NULLs fill gaps on either side):
Result: Alice (Engineering), Bob (NULL), Carol (NULL), NULL (Marketing).

---

**CROSS JOIN** — Every combination of rows from both tables (Cartesian product):
3 employees × 2 departments = **6 rows**. Used for generating combinations or test data.

---

**Venn diagram intuition:**

```
       employees    departments
        ┌───────┐   ┌───────┐
        │       │   │       │
        │  Bob  │   │ Mktg  │
        │ Carol ├───┤       │
        │       │Ali│       │
        └───────┘   └───────┘

INNER JOIN  = only the overlap (Alice)
LEFT JOIN   = left circle fully (Alice, Bob, Carol)
RIGHT JOIN  = right circle fully (Alice, Marketing)
FULL JOIN   = entire Venn diagram
```

## Q4: What is the difference between INNER JOIN and LEFT JOIN?

This is the most commonly confused join pair in interviews.

**INNER JOIN** — Returns only rows where a match exists in BOTH tables. Rows without a match are dropped entirely.

**LEFT JOIN** — Returns ALL rows from the left table. If a match exists in the right table, values are filled in. If not, the right-table columns are NULL.

```sql
-- Given: orders table has order_ids 1, 2, 3
-- customers table has entries for orders 1 and 2 only

-- INNER JOIN: only orders that have a matching customer (orders 1 and 2)
SELECT o.order_id, c.name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
-- Returns 2 rows

-- LEFT JOIN: ALL orders, NULL for those without a customer (order 3 appears with NULL name)
SELECT o.order_id, c.name
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id;
-- Returns 3 rows
```

**Key use of LEFT JOIN — find records with NO match (anti-join pattern):**
```sql
-- Find orders that have no customer assigned yet
SELECT o.order_id
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;  -- NULL means no match was found in customers
```

**Intuition:** INNER JOIN finds only the pairs. LEFT JOIN finds all the pairs AND the loners from the left side.

## Q5: What is the difference between WHERE and HAVING?

Both filter rows, but they apply at different stages of query execution:

| | WHERE | HAVING |
|---|---|---|
| **When applied** | Before GROUP BY — filters individual rows | After GROUP BY — filters aggregated groups |
| **Can reference** | Column values | Aggregate functions (COUNT, SUM, AVG) |

```sql
SELECT dept, AVG(salary) AS avg_salary
FROM employees
WHERE salary > 40000          -- Step 3: remove low earners BEFORE computing group averages
GROUP BY dept
HAVING AVG(salary) > 70000;  -- Step 5: keep only departments where the GROUP average > 70k
```

**Step-by-step walkthrough:**
1. FROM: load all rows from employees
2. WHERE: keep only rows where `salary > 40000` (individual row filter — affects which rows enter the groups)
3. GROUP BY: group remaining rows by `dept`
4. HAVING: keep only groups where `AVG(salary) > 70000` (group-level filter — runs AFTER the average is computed)
5. SELECT: return `dept` and `avg_salary`

**Common mistake — this fails:**
```sql
SELECT dept, AVG(salary)
FROM employees
WHERE AVG(salary) > 70000  -- ERROR: WHERE cannot see aggregate functions
GROUP BY dept;
```

**Intuition:** WHERE is the bouncer at the door (checks each person before they enter). HAVING is the rule for the whole table (checks each group after everyone is seated).

## Q6: What is GROUP BY and how does it work?

GROUP BY collapses multiple rows that share the same column value into a single summary row. You then use aggregate functions (SUM, COUNT, AVG) to summarize each group.

**Example — total sales and number of orders per region:**

`sales` table:
| region | amount |
|---|---|
| North | 100 |
| South | 200 |
| North | 150 |
| South | 300 |

```sql
SELECT region, SUM(amount) AS total, COUNT(*) AS num_orders
FROM sales
GROUP BY region;
```

Result:
| region | total | num_orders |
|---|---|---|
| North | 250 | 2 |
| South | 500 | 2 |

**The golden rule:** Every column in SELECT that is NOT inside an aggregate function MUST appear in GROUP BY.

```sql
-- This FAILS: amount is neither grouped nor aggregated
SELECT region, amount, SUM(amount)
FROM sales
GROUP BY region;

-- This works: amount is inside SUM
SELECT region, SUM(amount)
FROM sales
GROUP BY region;
```

**Group by multiple columns:**
```sql
SELECT region, product, SUM(amount)
FROM sales
GROUP BY region, product;  -- one row per unique (region, product) combination
```

**Intuition:** GROUP BY is like sorting receipts into piles by category, then totalling or counting each pile. Every pile gets exactly one summary row.

## Q7: What are aggregate functions?

Aggregate functions compute a single value from a group of rows. They collapse many values into one.

| Function | What it computes | NULL handling |
|---|---|---|
| `COUNT(*)` | Count of all rows, including NULLs | Includes NULLs |
| `COUNT(col)` | Count of non-NULL values in a column | **Skips NULLs** |
| `SUM(col)` | Sum of all values | Skips NULLs |
| `AVG(col)` | Mean of all values | Skips NULLs (does NOT count NULLs in denominator) |
| `MIN(col)` | Smallest value | Skips NULLs |
| `MAX(col)` | Largest value | Skips NULLs |

**Key gotcha — COUNT(*) vs COUNT(col):**
```sql
-- employees: [Alice: 90k, Bob: NULL salary, Carol: 75k]

SELECT COUNT(*) FROM employees;       -- 3 (every row)
SELECT COUNT(salary) FROM employees;  -- 2 (skips the NULL row for Bob)
```

**AVG gotcha with NULLs:**
```sql
-- salaries: [90000, NULL, 75000]
SELECT AVG(salary) FROM employees;
-- Returns (90000 + 75000) / 2 = 82500  (NOT divided by 3 — NULL is excluded)
```

**Using aggregates with GROUP BY:**
```sql
SELECT dept, COUNT(*) AS headcount, AVG(salary) AS avg_pay, MAX(salary) AS top_pay
FROM employees
GROUP BY dept;
```

**Intuition:** Aggregates are the "fold" operation — they turn a tall stack of rows into a single number. The NULL-skipping behavior is intentional (unknown values shouldn't influence summary statistics) but often surprises beginners.

## Q8: What are window functions? Explain ROW_NUMBER, RANK, and DENSE_RANK.

Window functions compute a value for each row using a "window" of related rows — without collapsing rows the way GROUP BY does. Every row keeps its identity while also seeing derived values across a group.

**General syntax:**
```sql
FUNCTION() OVER (PARTITION BY col ORDER BY col)
-- PARTITION BY: divides rows into groups (like GROUP BY but keeps all rows)
-- ORDER BY: determines the ordering within each partition
```

**Setup — employee salaries by department:**
| name | dept | salary |
|---|---|---|
| Alice | Eng | 120k |
| Bob | Eng | 100k |
| Carol | Eng | 100k |
| Dave | Mkt | 90k |
| Eve | Mkt | 80k |

**ROW_NUMBER()** — assigns a unique sequential number. No ties — two rows with equal values still get different numbers (arbitrary tiebreak):
```sql
SELECT name, salary,
  ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
FROM employees;
```
In Eng: Alice=1, Bob=2, Carol=3 (both 100k but different numbers)

**RANK()** — same rank for ties, then skips numbers:
In Eng: Alice=1, Bob=2, Carol=2, next rank would be **4** (gap because two people tied for 2nd)

**DENSE_RANK()** — same rank for ties, no gaps:
In Eng: Alice=1, Bob=2, Carol=2, next rank is **3** (no gap)

**Side-by-side comparison:**
| name | salary | ROW_NUMBER | RANK | DENSE_RANK |
|---|---|---|---|---|
| Alice | 120k | 1 | 1 | 1 |
| Bob | 100k | 2 | 2 | 2 |
| Carol | 100k | 3 | 2 | 2 |
| Dave (next in line) | 80k | 4 | 4 | 3 |

**Classic interview problem — top earner per department:**
```sql
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
) ranked
WHERE rn = 1;
```

**Other frequently tested window functions:**
```sql
LAG(salary, 1)  OVER (ORDER BY hire_date)  -- previous row's salary (compare month-over-month)
LEAD(salary, 1) OVER (ORDER BY hire_date)  -- next row's salary
SUM(salary) OVER (PARTITION BY dept)       -- department total on each row (no grouping)
SUM(salary) OVER (ORDER BY hire_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)  -- running total
NTILE(4) OVER (ORDER BY salary DESC)       -- salary quartile (1=top 25%, 4=bottom 25%)
```

**Intuition:** GROUP BY collapses rows into summary rows. Window functions keep all rows intact and add a new computed column alongside them.

## Q9: What is a subquery? When do you use it vs a CTE?

**Subquery:** A query nested inside another query. Written inline, wrapped in parentheses.

```sql
-- Find employees earning above the company average
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);
-- The inner query runs first, returns a single number (e.g., 82500)
-- The outer WHERE then filters rows against that number
```

**CTE (Common Table Expression):** A named temporary result set defined with `WITH`. Logically equivalent to a subquery but written at the top, making it readable and reusable.

```sql
WITH avg_salary AS (
  SELECT AVG(salary) AS avg_sal FROM employees
)
SELECT e.name, e.salary
FROM employees e
CROSS JOIN avg_salary
WHERE e.salary > avg_salary.avg_sal;
```

**When to use each:**

| | Subquery | CTE |
|---|---|---|
| **Readability** | OK for one level; messy when nested 3+ deep | Clean — reads top to bottom like a recipe |
| **Reusability** | Must repeat the same logic each time | Define once, reference multiple times |
| **Debugging** | Hard to isolate a single step | Run each WITH block independently |
| **Recursive queries** | Not possible | Supported — great for hierarchies/trees |

**Correlated subquery** — the inner query references the outer query and runs once per row. Powerful but can be slow:
```sql
-- For each employee, find their rank within their department
SELECT name, salary,
  (SELECT COUNT(*) + 1
   FROM employees e2
   WHERE e2.dept = e1.dept AND e2.salary > e1.salary) AS rank_in_dept
FROM employees e1;
-- Runs the inner query once per employee row — use window functions for the same result more efficiently
```

**Rule of thumb:** Use a subquery for a quick one-liner. Switch to a CTE as soon as the logic is reused or the query is more than two levels deep.

## Q10: What is the difference between UNION and UNION ALL?

Both combine results from two SELECT statements by stacking rows vertically.

| | UNION | UNION ALL |
|---|---|---|
| **Duplicates** | Removes duplicate rows | Keeps every row including duplicates |
| **Performance** | Slower — must sort to find and remove duplicates | Faster — no deduplication work |
| **When to use** | When you want only unique rows | When duplicates are expected or acceptable |

```sql
-- Users from two regional databases
SELECT user_id FROM us_users
UNION
SELECT user_id FROM eu_users;
-- If user_id 101 exists in both tables, it appears ONCE

SELECT user_id FROM us_users
UNION ALL
SELECT user_id FROM eu_users;
-- If user_id 101 exists in both tables, it appears TWICE
```

**Requirement:** Both SELECT statements must return the same number of columns, with compatible data types. Column names come from the first SELECT.

```sql
-- WRONG: different number of columns
SELECT id, name FROM us_users
UNION
SELECT id FROM eu_users;   -- ERROR

-- Workaround: pad with NULL
SELECT id, name FROM us_users
UNION
SELECT id, NULL AS name FROM eu_users;
```

**Intuition:** UNION ALL is stacking two spreadsheets. UNION is stacking then deduplicating. Use UNION ALL by default — it's faster and explicit about keeping everything. Only use UNION when you specifically need deduplication.

## Q11: How does SQL handle NULL values?

**NULL means "unknown" or "missing" — it is not zero, not an empty string, not false.**

**Three critical rules:**

1. **Any arithmetic with NULL returns NULL:** `NULL + 5 = NULL`, `NULL * 0 = NULL`
2. **Any comparison with NULL returns NULL (not TRUE or FALSE):** `NULL = NULL → NULL`, `NULL > 5 → NULL`
3. **Because of rule 2, `WHERE col = NULL` always returns zero rows.** Use `IS NULL` instead.

```sql
-- WRONG: returns no rows, silently
SELECT * FROM employees WHERE salary = NULL;

-- CORRECT
SELECT * FROM employees WHERE salary IS NULL;
SELECT * FROM employees WHERE salary IS NOT NULL;
```

**COALESCE — return the first non-NULL value in a list:**
```sql
SELECT name, COALESCE(salary, 0) AS salary     -- replace NULL with 0
FROM employees;

COALESCE(phone, mobile, email, 'no contact')   -- try each in order, return first non-NULL
```

**NULLIF — return NULL if two values are equal (classic divide-by-zero prevention):**
```sql
SELECT sales / NULLIF(visits, 0) AS conversion_rate
-- If visits = 0: NULLIF returns NULL → division returns NULL (not an error)
-- If visits > 0: NULLIF returns visits → normal division
FROM traffic;
```

**How NULLs behave in aggregates:**
```sql
-- Salaries: [90000, NULL, 75000]
AVG(salary)   →  82500     (NULL skipped, divides by 2 not 3)
SUM(salary)   →  165000    (NULL skipped)
COUNT(salary) →  2         (NULL skipped)
COUNT(*)      →  3         (counts every row including the NULL one)
MIN(salary)   →  75000     (NULL skipped)
```

**NULL in ORDER BY:** NULLs sort last by default in most databases (ASC). Use `NULLS FIRST` or `NULLS LAST` to control placement.

**Intuition:** Think of NULL as an unanswered survey question. You can't say it equals anything — you can only ask "is it blank?"

## Q12: What is a self-join? Give a real-world example.

A self-join joins a table to itself. Useful when rows in the same table are related to each other — the most classic example is an employee-manager hierarchy stored in a single table.

**Example — employee-manager table:**
| emp_id | name | manager_id |
|---|---|---|
| 1 | Alice (CEO) | NULL |
| 2 | Bob | 1 |
| 3 | Carol | 1 |
| 4 | Dave | 2 |

```sql
-- Show each employee alongside their manager's name
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;
-- Alias the same table twice: e = employee, m = manager
```

Result:
| employee | manager |
|---|---|
| Alice | NULL |
| Bob | Alice |
| Carol | Alice |
| Dave | Bob |

**Another use — find all pairs of employees in the same department:**
```sql
SELECT a.name AS emp1, b.name AS emp2, a.dept
FROM employees a
JOIN employees b ON a.dept = b.dept
           AND a.emp_id < b.emp_id;  -- prevents duplicate pairs: (Alice, Bob) and (Bob, Alice)
```

**Intuition:** You alias the same table twice and treat each alias as if it were a different table. The join condition defines the relationship between the two "copies." Always give each alias a meaningful name to avoid confusion.

## Q13: Write a query to find the Nth highest salary.

**Method 1 — DENSE_RANK (recommended, handles ties correctly):**
```sql
SELECT salary FROM (
  SELECT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 3;  -- change 3 to any N
```

**Method 2 — DISTINCT + LIMIT/OFFSET (simpler, less robust for ties):**
```sql
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 2;  -- OFFSET = N-1, so OFFSET 2 gives the 3rd highest
```

**Why DENSE_RANK is better:**

Step-by-step for N=2 (2nd highest), salaries = [120k, 100k, 100k, 80k]:
- DENSE_RANK assigns: 120k→1, 100k→2, 100k→2, 80k→3
- WHERE rnk = 2 → returns 100k ✓ (correctly identifies the 2nd distinct salary)

With LIMIT/OFFSET:
- DISTINCT values sorted desc: [120k, 100k, 80k]
- OFFSET 1 → 100k ✓ (works in this case, but breaks if ties span multiple ranks)

**What if no Nth highest exists?** DENSE_RANK query returns zero rows (safe). Wrap in COALESCE if you need a default:
```sql
SELECT COALESCE(
  (SELECT salary FROM (...) WHERE rnk = 5),
  NULL
) AS fifth_highest;
```

## Q14: What is the difference between DELETE, TRUNCATE, and DROP?

All three remove data but work at different levels:

| | DELETE | TRUNCATE | DROP |
|---|---|---|---|
| **What it removes** | Selected rows (or all if no WHERE) | All rows in the table | Entire table (structure + all data) |
| **WHERE clause** | Yes — can filter specific rows | No — always removes all rows | N/A |
| **Can rollback** | Yes (DML, fully logged) | Depends on database | No |
| **Resets AUTO_INCREMENT** | No | Yes | Yes |
| **Speed** | Slower (row-by-row, logs each) | Faster (page deallocation) | Instant |
| **Table structure** | Preserved | Preserved | Destroyed |

```sql
DELETE FROM employees WHERE dept = 'Marketing';  -- removes specific rows
TRUNCATE TABLE employees;                         -- empties the table, keeps structure
DROP TABLE employees;                             -- table is completely gone
```

**Common interview trick question:** "Can you roll back a TRUNCATE?"
- In PostgreSQL and SQL Server: yes — TRUNCATE is transactional.
- In MySQL: no — TRUNCATE implicitly commits.

**Intuition:**
- DELETE = erase specific words from a document
- TRUNCATE = erase all text but keep the blank document
- DROP = shred the document entirely

## Q15: What are indexes and when should you use them?

An index is a data structure (typically a B-tree) that the database maintains alongside a table to speed up queries — at the cost of extra storage and slightly slower writes.

**Without index:** Full table scan — the database reads every row to find matches. `O(n)`.
**With index:** The database jumps to matching rows via the index tree. `O(log n)`.

```sql
-- Create an index on the email column
CREATE INDEX idx_emp_email ON employees(email);

-- Now fast even on a 10-million-row table
SELECT * FROM employees WHERE email = 'alice@company.com';
```

**When to add an index:**
- Columns frequently used in `WHERE`, `JOIN ON`, or `ORDER BY`
- Foreign key columns (makes JOINs fast)
- Columns with high cardinality (many distinct values — user_id, email, order_id)

**When NOT to index:**
- Small tables — a full scan is faster than index overhead
- Low-cardinality columns (e.g., a boolean `is_active` column — the index barely helps)
- Tables with very heavy write load — every INSERT/UPDATE must also update the index

**Composite index — column order matters:**
```sql
CREATE INDEX idx_name ON employees(last_name, first_name);
-- Helps queries filtering by: last_name alone, OR (last_name + first_name)
-- Does NOT help queries filtering by: first_name alone
-- Rule: put the most selective or most-filtered column first
```

**Covering index:** An index that includes all columns needed by the query — the database never has to read the actual table rows, just the index.

**Intuition:** An index is like the index at the back of a textbook — great for looking up specific topics instantly, useless if you're reading every page anyway.
