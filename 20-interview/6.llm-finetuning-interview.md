# LoRA Parameters

---

## Q1: What are LoRA's key parameters, and what are the right values for LLM fine-tuning?

LoRA (Low-Rank Adaptation) inserts trainable rank-$r$ decomposition matrices into frozen pretrained weight matrices. Instead of updating $W \in \mathbb{R}^{d \times k}$, it adds:

$$W' = W + \Delta W = W + BA, \quad B \in \mathbb{R}^{d \times r},\; A \in \mathbb{R}^{r \times k}, \quad r \ll \min(d, k)$$

Only $A$ and $B$ are trained. For a 7B-parameter model with $r=16$, LoRA adapters are ~0.1% of total parameters — GPU memory drops from ~80 GB (full finetune in bf16) to ~6 GB (4-bit QLoRA + LoRA).

**Every LoRA parameter explained with optimal values:**

### `r` — LoRA rank (default: 16)

The number of columns in $A$ and rows in $B$. Determines the expressiveness of the adapter.

| r | Parameters added | Use case |
|---|---|---|
| 4 | Minimal | Style transfer, very constrained VRAM |
| 8 | Low | Short conversation fine-tunes; works well for instruction tuning |
| **16** | **Standard** | **Unsloth and PEFT default; best starting point** |
| 32–64 | High | Complex reasoning tasks; domain adaptation with large datasets |
| 128+ | Very high | Approaching full fine-tune quality; diminishing returns past 64 |

**Rule of thumb:** start at $r=16$. If validation loss is high, double to 32. If you need maximum quality and have VRAM, use $r=64$. Going beyond 64 rarely beats full fine-tuning and wastes memory.

### `lora_alpha` — scaling factor (default: 16 or 32)

The adapter output is scaled by $\alpha / r$:

$$\Delta W = \frac{\alpha}{r} \cdot BA$$

This controls how strongly the LoRA update affects the model.

| alpha / r ratio | Effect |
|---|---|
| $\alpha = r$ (ratio = 1) | Conservative — adapter changes are small relative to pretrained weights |
| $\alpha = 2r$ (ratio = 2) | **Most common** — doubles the effective LR of adapters; Unsloth default |
| $\alpha > 2r$ | Aggressive — adapter can overwrite pretrained knowledge |

**Unsloth default: `lora_alpha = 16` when `r = 16`** (ratio = 1, conservative). Some practitioners use `lora_alpha = 32` with `r = 16` (ratio = 2) to get stronger adaptation without increasing $r$.

**Intuition:** $\alpha/r$ acts as a per-adapter learning rate multiplier. Keeping $\alpha = r$ means the adapter training is balanced with the pre-trained weight scale. Setting $\alpha = 2r$ doubles how fast the adapter learns.

### `lora_dropout` — dropout on adapter layers (default: 0)

Applies dropout to LoRA adapter activations during training.

**Unsloth and PEFT both recommend 0.** The reason: LoRA adapters are already a tiny fraction of the full model (rank-16 adds ~0.1% parameters). Dropout on such small matrices is more disruptive than regularising — it breaks gradient flow through the already-constrained low-rank pathway without meaningful regularisation benefit.

Use non-zero (`0.05–0.1`) only when you observe clear overfitting on a small dataset.

### `target_modules` — which weight matrices to adapt

Specifies which layers get LoRA adapters.

```python
# Full attention + FFN (Unsloth recommended for best quality)
target_modules = ["q_proj", "k_proj", "v_proj", "o_proj",
                  "gate_proj", "up_proj", "down_proj"]

# Attention only (PEFT default — less memory, less quality)
target_modules = ["q_proj", "v_proj"]
```

**Why these specific projections?**
- `q_proj`, `k_proj`, `v_proj`, `o_proj` — the four attention projections. Adapting these changes *what* the model attends to and *how* it combines attention outputs.
- `gate_proj`, `up_proj`, `down_proj` — the FFN / MLP layers. These store factual knowledge and task-specific skills. Adapting them is critical for knowledge-heavy tasks.

**Unsloth recommendation:** always include all 7 projections. The FFN layers often matter more than attention for task adaptation. Omitting them limits the adapter's expressiveness.

### `bias` — whether to train bias terms (default: `"none"`)

| Setting | Effect |
|---|---|
| `"none"` | Biases frozen — recommended; avoids parameter drift |
| `"all"` | All biases trainable — marginal quality gain, slight memory cost |
| `"lora_only"` | Only biases in LoRA layers — rarely used |

### `use_gradient_checkpointing` — VRAM saving (default: `"unsloth"`)

Recomputes intermediate activations during the backward pass instead of storing them. Saves ~30% VRAM at the cost of ~10% training speed.

- `True` (PyTorch standard): works but recomputes everything
- `"unsloth"`: Unsloth's custom implementation — 30% more VRAM savings than standard, by checkpointing only the most memory-intensive layers

### `use_rslora` — rank-stabilized LoRA (default: False)

RSLoRA changes the scaling from $\alpha/r$ to $\alpha/\sqrt{r}$, which keeps gradient norms stable as $r$ increases. Enables training with larger ranks without the instability that occurs when $r \gg 16$.

Enable when: `r ≥ 64` or when you observe training instability at high ranks.

### `use_dora` — weight-decomposed LoRA (default: False)

DoRA decomposes $W$ into magnitude and direction components, adapting only the direction with LoRA. Closes the quality gap between LoRA and full fine-tuning (within 0.5% of full FT on most tasks) at ~1.5× the VRAM cost of standard LoRA.

Enable when: maximum quality matters and you have VRAM headroom.

**Complete Unsloth LoRA configuration example:**

```python
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/llama-3-8b-bnb-4bit",
    max_seq_length=2048,   # context length; set to task max
    dtype=None,            # auto-detect: bf16 on Ampere+, fp16 otherwise
    load_in_4bit=True,     # QLoRA: quantize base model to 4-bit
)

model = FastLanguageModel.get_peft_model(
    model,
    r=16,                  # rank: 16 is the standard starting point
    lora_alpha=16,         # scaling: equal to r (conservative)
    lora_dropout=0,        # 0 recommended for LoRA; no regularisation benefit
    target_modules=[       # all attention + FFN projections
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    bias="none",
    use_gradient_checkpointing="unsloth",  # saves ~30% VRAM
    random_state=3407,
    use_rslora=False,      # set True if r >= 64
    use_dora=False,        # set True if you need near-full-FT quality
)
```

# SFTTrainer / TrainingArguments

---

## Q2: What are the key SFTTrainer / TrainingArguments settings for LLM fine-tuning, and what are their optimal values?

`SFTTrainer` (from `trl`) wraps HuggingFace `Trainer` with supervised fine-tuning conveniences (chat template formatting, packing, etc.). The training behaviour is controlled by `TrainingArguments`. Here is every parameter that matters, what it does, and the recommended value.

### Batch size and gradient accumulation

**`per_device_train_batch_size`** (default: 8 → use **2** for LLM fine-tuning)

Number of samples processed per GPU per step. LLMs use large sequence lengths (2048+ tokens), so each sample consumes significant VRAM. Setting this too high → OOM; too low → noisy gradient estimates.

**`gradient_accumulation_steps`** (default: 1 → use **4**)

Accumulates gradients over N mini-batches before an optimizer step. Effective batch = `per_device_train_batch_size × gradient_accumulation_steps × num_GPUs`.

With `batch=2, accum=4, 1 GPU`: effective batch = 8 — same gradient quality as batch=8 but uses 4× less VRAM per step.

**Unsloth recommendation:** `batch=2, accum=4` for 8B models on a single A100-80GB. For 70B QLoRA: `batch=1, accum=8`.

### Learning rate

**`learning_rate`** (use **2e-4** for LoRA; **1e-5 to 5e-5** for full fine-tune)

For LoRA fine-tuning, a higher LR (2e-4) is safe because only the small adapter matrices are updated — the pretrained weights are frozen and cannot be catastrophically overwritten. For full fine-tuning, use a much lower LR to avoid forgetting the pretrained representations.

| Method | Recommended LR |
|---|---|
| Full fine-tune | 1e-5 – 5e-5 |
| LoRA fine-tune | 1e-4 – 3e-4 |
| QLoRA (4-bit) | 2e-4 (Unsloth default) |
| Continued pretraining | 1e-5 – 1e-4 |

### Optimizer

**`optim`** (use **`"adamw_8bit"`**)

8-bit AdamW from `bitsandbytes` stores optimizer states in 8-bit instead of 32-bit, reducing optimizer memory by 4×. For a 7B model, AdamW states normally consume ~28 GB; 8-bit AdamW brings this to ~7 GB.

| optim value | Memory | Speed | Use when |
|---|---|---|---|
| `"adamw_torch"` | Full (32-bit) | Baseline | Full fine-tune on multi-GPU |
| `"adamw_8bit"` | 4× smaller | Same | **QLoRA / LoRA; Unsloth default** |
| `"paged_adamw_8bit"` | Paged (spills to CPU) | Slightly slower | Very constrained VRAM |
| `"adamw_bnb_8bit"` | Same as 8bit | Same | Alias for above |

### LR scheduler

**`lr_scheduler_type`** (use **`"linear"`** or **`"cosine"`**)

| Scheduler | Behaviour | Best for |
|---|---|---|
| `"linear"` | Linear decay from peak to 0 | Short runs (< 1000 steps); simple; Unsloth default |
| `"cosine"` | Smooth cosine decay | Longer runs; avoids sharp LR changes |
| `"cosine_with_restarts"` | Cosine with periodic resets | When training on diverse datasets |
| `"constant_with_warmup"` | Flat LR after warmup | Experimental; rarely better than cosine |

**`warmup_ratio`** (use **0.03 – 0.05** i.e. 3–5% of total steps)
or **`warmup_steps`** (use **5–100** for short fine-tunes, **500–4000** for full pre-training)

Warmup prevents catastrophic updates in early steps. For short fine-tunes (< 1000 steps), `warmup_steps=5` is enough.

### Precision

**`bf16=True`** on Ampere+ GPUs (A100, H100, RTX 3090+). **`fp16=True`** on older GPUs (V100, T4).

BF16 has the same dynamic range as FP32 (8 exponent bits vs FP16's 5), making it much more numerically stable for LLM training. It prevents loss spikes from large gradient magnitudes that frequently occur in long-context fine-tuning.

```python
# Auto-detect in Unsloth:
from unsloth import is_bfloat16_supported
bf16 = is_bfloat16_supported()
fp16 = not is_bfloat16_supported()
```

### Weight decay and gradient clipping

**`weight_decay`** (use **0.01**)

L2 regularisation applied to non-bias, non-LayerNorm parameters. Helps prevent the adapter weights from growing too large. Unsloth default is 0.01.

**`max_grad_norm`** (use **1.0**)

Clips the gradient norm if it exceeds this threshold. Prevents exploding gradients in long sequences. Standard value is 1.0 across GPT-2, LLaMA, Mistral training.

### Steps and epochs

**`num_train_epochs`** (use **1–3** for instruction fine-tuning)

More than 3 epochs on instruction datasets typically causes overfitting — the model begins to memorise exact phrasings. Unsloth and Alpaca fine-tuning guides use 1–2 epochs.

**`max_steps`** (use for quick tests: **60–200**)

Takes precedence over `num_train_epochs`. Use `max_steps=60` to verify training works before committing to a full run.

**`logging_steps`** (use **1** for short runs, **10–25** for longer runs)

How often to log training loss to console / W&B. Set to 1 during development so you see every step.

**`save_steps`** / **`save_strategy`**: use `"epoch"` or a fixed step count. Always save the final checkpoint.

### Full SFTTrainer configuration (Unsloth-optimised):

```python
from trl import SFTTrainer
from transformers import TrainingArguments
from unsloth import is_bfloat16_supported

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=dataset,
    dataset_text_field="text",
    max_seq_length=2048,          # match max_seq_length from model load
    dataset_num_proc=2,           # parallel tokenisation workers
    packing=False,                # True packs short samples together (faster, less padding waste)
    args=TrainingArguments(
        per_device_train_batch_size=2,       # small batch for VRAM
        gradient_accumulation_steps=4,       # effective batch = 8
        warmup_steps=5,                      # or warmup_ratio=0.03 for longer runs
        num_train_epochs=1,                  # 1-3 epochs; more risks overfitting
        learning_rate=2e-4,                  # LoRA standard; use 1e-5 for full FT
        fp16=not is_bfloat16_supported(),
        bf16=is_bfloat16_supported(),
        logging_steps=1,
        optim="adamw_8bit",                  # 4× less optimizer memory
        weight_decay=0.01,
        lr_scheduler_type="linear",          # or "cosine" for longer runs
        seed=3407,
        output_dir="outputs",
        max_grad_norm=1.0,
    ),
)
trainer.train()
```

**Complete parameter decision table:**

| Parameter | Quick test | Production fine-tune | Full fine-tune |
|---|---|---|---|
| `r` | 8 | 16 | — |
| `lora_alpha` | 8 | 16 | — |
| `lora_dropout` | 0 | 0 | — |
| `target_modules` | q,v only | all 7 | all layers |
| `per_device_train_batch_size` | 2 | 2 | 4–8 |
| `gradient_accumulation_steps` | 1 | 4 | 4–16 |
| `learning_rate` | 2e-4 | 2e-4 | 2e-5 |
| `num_train_epochs` | 1 | 1–3 | 1–2 |
| `optim` | adamw_8bit | adamw_8bit | adamw_torch |
| `lr_scheduler_type` | linear | cosine | cosine |
| `warmup_steps` | 5 | 100 | 500–4000 |
| `weight_decay` | 0.01 | 0.01 | 0.01–0.1 |
| `max_grad_norm` | 1.0 | 1.0 | 1.0 |
| `bf16` / `fp16` | auto | bf16 if A100+ | bf16 |
| `load_in_4bit` | True | True | False |

**Interview one-liner:** for LLM LoRA fine-tuning the three parameters that matter most are `learning_rate` (2e-4), `r` (16), and `per_device_train_batch_size × gradient_accumulation_steps` (effective batch ≥ 8); everything else can be left at defaults and adjusted only if you see instability or overfitting.
