## Q1: What are recommender systems and what are the main types?

**Intuition:** A recommender system answers the question "what will this specific user want next?" by learning patterns from the history of what many users have liked, clicked, bought, or watched. Think of it as a personalized matchmaker between users and items at scale.

**Three main families:**

**1. Collaborative Filtering (CF)**
"Users who behaved like you also liked these items."
- Uses only user-item interaction data (ratings, clicks, purchases)
- No item content needed — the pattern emerges from collective behavior
- Examples: Netflix "Because you watched X", Amazon "Customers also bought"

**2. Content-Based Filtering**
"Show you more items similar to what you already liked."
- Uses item features (genre, keywords, audio properties, embeddings)
- Builds a user profile from their past liked items and matches it to new items
- Works for a single user in isolation — doesn't need data from others
- Examples: Pandora's music genome, news article recommendations by topic

**3. Hybrid Systems**
Combine CF + content-based to get benefits of both.
Most production systems (Netflix, Spotify, YouTube, TikTok) are hybrid.

| | Collaborative Filtering | Content-Based |
|---|---|---|
| **Data needed** | User-item interactions | Item features |
| **New user cold start** | Problem — no history | OK — use item features |
| **New item cold start** | Problem — no ratings yet | OK — use item content |
| **Serendipity** | High — discovers unexpected items | Low — tends toward filter bubble |
| **Production default** | Yes — matrix factorization / two-tower | Yes — fallback for cold start |

## Q2: How is training data prepared for a recommender system?

**Intuition:** The training data is a table of "who interacted with what, when, and how strongly." The central challenge is extreme sparsity — a user on Netflix has watched maybe 200 out of 10 million titles (99.998% of interactions are missing).

**Step 1 — Build the user-item interaction matrix**

The core data structure: rows = users, columns = items, cells = interaction signal.

| | Movie A | Movie B | Movie C | Movie D |
|---|---|---|---|---|
| User 1 | 5.0 | — | 3.0 | — |
| User 2 | — | 4.0 | — | 2.0 |
| User 3 | 4.5 | — | — | 5.0 |

Most cells are empty (user hasn't seen the item). A 100M-user × 10M-item platform has 99.9%+ sparsity.

**Step 2 — Collect interaction signals**

| Signal type | Examples | Quality |
|---|---|---|
| Explicit feedback | Star ratings (1–5), thumbs up/down | High quality, low volume |
| Implicit feedback | Clicks, purchases, watch time, add-to-cart, replays, search | Noisy, but very high volume |

Most production systems rely on implicit feedback — users rarely rate things, but they click and watch constantly.

**Step 3 — Convert implicit signals into training labels**

```
Positive sample:  user purchased item          → label = 1
Negative sample:  item shown but not clicked   → label = 0 (weak negative)
Watch threshold:  watched > 70% of video       → positive
                  watched < 5% of video        → negative
```

**Step 4 — Negative sampling (critical)**

The matrix has mostly zeros. Training on ALL zeros as negatives would teach the model to predict zero everywhere. Fix:
- **Random negative sampling:** for each positive, randomly sample K items the user didn't interact with as negatives. Typical ratio: 1 positive to 4–10 negatives.
- **Hard negative sampling:** sample items the user was exposed to but ignored (harder = better training signal)
- **Popularity-weighted negatives:** sample negatives proportional to item popularity so the model learns to distinguish genuine interest from just popular items

**Step 5 — Augment with features**

Each (user, item) training pair gets enriched:

| Feature type | Examples |
|---|---|
| User features | Account age, device, location, genre preferences, recent history embedding |
| Item features | Genre, release year, language, popularity, content embedding |
| Context features | Time of day, day of week, current session length, referral source |

**Step 6 — Temporal train/eval split**

Always split by time, not randomly:
- Train: all interactions before date T
- Validation: interactions in [T, T+7 days]
- Test: interactions after T+7 days

Random split leaks future interactions into training — the model would "know" that User 1 liked Movie A even though that happened after deployment. This is a form of data leakage.

## Q3: What is collaborative filtering? User-based vs item-based?

**Intuition:** Collaborative filtering is the "wisdom of the crowd" approach. You don't need to know anything about the items themselves — you just need to observe that people with similar behavior tend to like the same things.

**User-based CF:** "Find users similar to you → recommend what they liked."

1. Compute similarity between User A and every other user (cosine similarity or Pearson correlation on their rating vectors)
2. Find the K nearest neighbors (most similar users)
3. Aggregate what those neighbors liked that User A hasn't seen
4. Recommend the top-scored unseen items

**Example:**
- User 1 liked: Inception, Interstellar, Tenet
- User 2 liked: Inception, Interstellar, The Prestige (very similar to User 1)
- User 1 hasn't seen The Prestige → recommend it

**Item-based CF:** "Find items similar to items you've liked → recommend those."

1. Compute similarity between every pair of items (using the column vectors of user ratings)
2. For each item User A liked, find its K most similar items
3. Recommend the top similar items User A hasn't seen

**Example:**
- Inception and Interstellar have similar rating vectors (the same users gave both high ratings)
- User 1 loved Inception → recommend Interstellar

**User-based vs Item-based:**

| | User-based | Item-based |
|---|---|---|
| **Intuition** | "People like you" | "Items like this" |
| **Stability** | User tastes shift over time | Item similarities are more stable |
| **Scalability** | Expensive — comparing billions of users | Better — item × item, fewer items than users |
| **Production use** | Rare at large scale | Common (Amazon's original CF was item-based) |

**Shared limitation:** As the platform grows, computing all pairwise similarities becomes O(n²) and prohibitively expensive. This is why matrix factorization and two-tower deep learning models replaced neighborhood-based CF at scale.

## Q4: What is content-based filtering?

**Intuition:** Instead of asking "who else liked this?", content-based filtering asks "what properties does this item have, and what properties has this user shown preference for?" It then matches the two profiles.

**How it works — step by step:**

**Step 1 — Build item profiles**
Represent each item as a feature vector:
- Movie: [genre_action=1, genre_drama=0, director_nolan=1, year=2010, ...]
- Article: TF-IDF vector over its words, or BERT sentence embedding
- Music track: tempo=128, energy=0.85, danceability=0.72, valence=0.60 (Spotify's audio features)

**Step 2 — Build user profiles**
Aggregate the feature vectors of items the user has interacted with:
- User profile = average of feature vectors of all liked items
- Or a weighted average (more recent interactions weighted higher)

**Step 3 — Score candidate items**
Compute cosine similarity between the user profile vector and each candidate item vector. Recommend top-N highest-similarity items.

**Example — movie preferences:**
- User liked: The Dark Knight [action=1, thriller=1, sci-fi=0] and Inception [action=1, thriller=0, sci-fi=1]
- User profile = average = [action=1.0, thriller=0.5, sci-fi=0.5]
- New movie Tenet [action=1, thriller=0.5, sci-fi=1.0] → high cosine similarity → recommend

**Strengths:**
- Works with just a few user interactions (bootstraps quickly)
- Explainable: "Recommended because you liked action films"
- No cold start for new items — just add the item's feature vector

**Weaknesses:**
- Filter bubble: user gets stuck in a loop of similar content, never discovers new genres
- Feature quality matters — if item descriptions are poor, recommendations are poor
- Misses social signal: "many people like you are also exploring jazz" is invisible to content-based

## Q5: What is matrix factorization? Explain SVD and ALS.

**Intuition:** Instead of storing the full sparse user-item matrix (millions × millions, mostly empty), matrix factorization learns compact representations: each user gets a short "taste vector" and each item gets a short "attribute vector." A user's predicted rating for an item is just the dot product of these two vectors.

**The key equation:**
$$R \approx U \cdot V^T$$
- R = user-item rating matrix (n_users × n_items, very sparse)
- U = user embedding matrix (n_users × k latent factors)
- V = item embedding matrix (n_items × k latent factors)
- k = number of latent factors — typically 50–300

**Predicted rating for user u, item i:**
$$\hat{r}_{ui} = \mathbf{u}_u \cdot \mathbf{v}_i = \sum_{f=1}^{k} u_{uf} \cdot v_{if}$$

**What are latent factors?** The model discovers them automatically. In a movie context, some dimensions roughly correspond to "action vs drama", "recent vs classic", "indie vs blockbuster" — but the model learns these without labels.

**SVD (Singular Value Decomposition):**
Classic matrix factorization: decomposes R = U Σ Vᵀ exactly for dense matrices. Problem: the rating matrix is 99%+ sparse. Simon Funk's modified SVD handles this by only minimizing error over observed ratings (ignoring blanks).

**ALS (Alternating Least Squares) — the production standard:**
- Fix V, solve for each user vector u analytically (closed-form least squares)
- Fix U, solve for each item vector v analytically
- Alternate until convergence

**Why ALS over gradient descent?**
- Each sub-problem has a closed-form solution → no learning rate tuning
- Highly parallelizable — each user's vector can be updated independently
- Handles implicit feedback natively with confidence weighting
- Used at Netflix, Spotify at scale (Spark MLlib's ALS is the default)

**Loss function:**
$$\min_{U, V} \sum_{(u,i) \in \text{observed}} (r_{ui} - \mathbf{u}_u \cdot \mathbf{v}_i)^2 + \lambda(\|\mathbf{u}_u\|^2 + \|\mathbf{v}_i\|^2)$$

The λ term is L2 regularization — prevents users/items with very few interactions from overfitting.

## Q6: What is the cold start problem and how do you solve it?

**Intuition:** A recommender learns from past behavior. What do you recommend to someone brand new with zero history? Or a brand new item that nobody has interacted with yet? That's cold start — the system has no signal to work with.

**Three types of cold start:**
1. **New user cold start** — signed up 5 minutes ago, zero interactions
2. **New item cold start** — just added to the catalog, no ratings or clicks yet
3. **New system cold start** — the entire platform is brand new with no data at all

**Solutions for new USER cold start:**

| Solution | How it works | Used by |
|---|---|---|
| Onboarding survey | Ask about preferences on first login (genres, artists, topics) | Spotify, Netflix |
| Popularity-based fallback | Show the most popular items globally or by demographic | Most platforms |
| Demographic cluster | Assign new user to a user cluster based on age/location/device, recommend that cluster's favorites | Amazon |
| Exploration session | Show diverse items, observe first few clicks, rapidly personalize | TikTok |

**Solutions for new ITEM cold start:**

| Solution | How it works |
|---|---|
| Content embedding | Use item features (text, image, tags) to generate an embedding. Find similar existing items and inherit their placement. |
| Exploration boost | Artificially inject the new item into a small fraction of recommendation slots to gather early signal fast |
| Hybrid model transition | Start with content-based embedding as the item vector; switch to CF embedding once enough interactions accumulate |

**Key insight:** Cold start is why production systems are hybrid. Pure CF fails at cold start, but content-based never needs historical interactions. A real system transitions from content-based to CF as interactions accumulate per item and per user.

## Q7: What is the difference between explicit and implicit feedback?

**Explicit feedback:** The user directly and intentionally expresses a preference.
- Star ratings, thumbs up/down, "Not Interested" button
- High quality signal — no ambiguity about what it means
- Low volume — most users rarely rate (rating fatigue)

**Implicit feedback:** Inferred from behavior, not a direct statement.
- Clicks, purchases, watch time, replays, search queries, scroll depth, add-to-cart
- Very high volume — every user action generates a data point
- Noisy — a click doesn't mean "loved it" (could be curiosity, misclick, or partial interest)

| | Explicit | Implicit |
|---|---|---|
| **Signal quality** | High | Noisy |
| **Volume** | Low | Very high |
| **Negative signal** | Clear (1-star = disliked) | Ambiguous (didn't click ≠ disliked — may not have seen it) |
| **Production reality** | Rare — Netflix even removed star ratings | Dominant — most systems are built on this |

**How to handle implicit feedback in the model:**

Treat it as a **positive-unlabeled (PU)** problem:
- Observed interactions = positive examples (user showed interest)
- Unobserved items ≠ negative examples (user may simply not have seen them)
- Use **confidence weighting**: a purchase gets high confidence; a single scroll-past gets low confidence

In weighted ALS: confidence $c_{ui} = 1 + \alpha \cdot r_{ui}$ where $r_{ui}$ is the raw interaction count and α controls how much each additional interaction increases confidence. The model fits observed interactions harder than the zeros.

## Q8: How do two-tower models work?

**Intuition:** A two-tower model learns separate neural network representations for users and items, then scores candidate items by computing similarity between the user embedding and each item embedding in vector space. It's the backbone of modern large-scale retrieval at Google, YouTube, and TikTok.

**Architecture:**

```
User Features ──► User Tower (MLP layers) ──► User Embedding (e.g., 256-dim)
                                                        │
                                              Dot product / Cosine similarity ──► Score
                                                        │
Item Features ──► Item Tower (MLP layers) ──► Item Embedding (e.g., 256-dim)
```

**User tower inputs:**
- Watched history (average of item embeddings, or sequence model output)
- User demographics, device, location
- Context: time of day, session length, how they arrived

**Item tower inputs:**
- Item ID embedding (learned)
- Content features: text description, genre tags, image embedding
- Popularity, recency, language

**Training objective:**
- Positive pair: (user, item they interacted with) → maximize similarity
- Negative pairs: (user, items they didn't interact with) → minimize similarity
- Loss: in-batch softmax cross-entropy (treating all other items in the batch as negatives)

**The key production insight — pre-computed item embeddings:**
During inference, all item embeddings are pre-computed and indexed offline.
At query time: only the user tower runs a forward pass (fast!), producing a user embedding.
Then an approximate nearest neighbor (ANN) search finds the most similar items in milliseconds.
This separation is what makes two-tower models work at billion-item scale.

**Two-tower = retrieval stage (returns top-K candidates).**
A heavier ranking model then re-scores those K candidates with richer cross-feature interactions. This two-stage funnel is universal at large-scale recommender systems.

## Q9: How does a recommender system work at inference time?

**Intuition:** You can't score all 10 million items in real time — that would take seconds per request. Instead, production systems use a funnel: start broad and fast, get progressively more precise, score a small final set deeply.

**The standard 3-stage inference pipeline:**

```
10,000,000 items
       │
       ▼ Stage 1: Candidate Retrieval  ← fast ANN search, rules, CF lookup
  1,000–10,000 candidates
       │
       ▼ Stage 2: Pre-ranking          ← lightweight model (logistic regression / tiny MLP)
   100–500 candidates
       │
       ▼ Stage 3: Ranking              ← full model, rich cross-features
    10–50 final recommendations
       │
       ▼ Post-processing               ← diversity, dedup, business rules, A/B routing
    Final feed / page
```

**Stage 1 — Candidate Retrieval (latency target: < 50ms)**
- **Two-tower ANN:** Pre-compute all item embeddings. At query time, run the user tower, then query FAISS / ScaNN for the nearest item embeddings.
- **CF lookup:** Pre-computed user-item similarity tables
- **Business rules:** Always include new releases, trending items, items from preferred categories

**Stage 2 — Pre-ranking (optional, latency target: < 20ms)**
A lightweight logistic regression or tiny MLP scores each candidate with basic features.
Eliminates obvious mismatches cheaply. Reduces 10K → 500.

**Stage 3 — Ranking (latency target: < 100ms)**
A full ML model (XGBoost, deep neural net with cross-feature interactions) scores each candidate with rich signals:
- User × item interaction features (has this user interacted with this creator before?)
- Real-time context (current session, trending signals)
- Historical CTR and purchase rate for this item segment
Output: predicted probability of engagement. Sort by score. Return top N.

**Post-processing:**
- Deduplicate: no two items from the same creator back-to-back
- Diversity: ensure not all items are the same category
- Business constraints: inject sponsored items, suppress out-of-stock or policy-violating content
- A/B routing: send 10% of traffic to experimental model

## Q10: How do you evaluate a recommender system?

**Intuition:** Unlike binary classification where one prediction is right or wrong, a recommender outputs a ranked list. Evaluation must reward putting the right items near the top of the list — not just anywhere in it.

**Offline setup for all metrics:** For each user, hold out their next K real interactions as ground truth. The model generates a ranked list of N recommendations. Compare the two.

---

**Precision@K** — Of the top K recommendations, what fraction did the user actually engage with?

$$\text{Precision@K} = \frac{\text{Relevant items in top K}}{K}$$

Example: K=5, user clicked 2 of the 5 recommended → Precision@5 = 0.40

---

**Recall@K** — Of all items the user actually engaged with, what fraction appeared in the top K?

$$\text{Recall@K} = \frac{\text{Relevant items in top K}}{\text{Total relevant items for user}}$$

Example: User had 10 real interactions; 3 appeared in the top-10 recommendations → Recall@10 = 0.30

---

**Hit Rate@K (HR@K)** — Did at least ONE relevant item appear in the top K? Binary per user, averaged across all users.

$$\text{HR@K} = \frac{\text{Users with ≥1 relevant item in top K}}{\text{Total users}}$$

Simple and intuitive: "What fraction of users received at least one good recommendation?"

---

**MRR (Mean Reciprocal Rank)** — How high up the list was the FIRST relevant item?

$$\text{MRR} = \frac{1}{|U|} \sum_{u} \frac{1}{\text{rank of first relevant item for user } u}$$

First relevant item at rank 1 → score 1.0; rank 2 → 0.5; rank 5 → 0.2. Averaged over all users.

---

**NDCG@K (Normalized Discounted Cumulative Gain)** — the gold standard for ranking quality. Rewards putting relevant items higher in the list via a logarithmic discount.

**Step 1 — DCG@K:**
$$\text{DCG@K} = \sum_{i=1}^{K} \frac{\text{rel}_i}{\log_2(i+1)}$$

rel_i = 1 if position i is relevant, 0 otherwise. Discount: rank 1 = 1.0, rank 2 = 0.63, rank 3 = 0.5.

**Step 2 — IDCG@K:** DCG if the list were in perfect order.

**Step 3:** NDCG@K = DCG@K / IDCG@K (0 to 1).

**Worked example (K=3), ground truth relevant = {B, C}:**
Model ranking: [A, B, C] → A is wrong, B at rank 2, C at rank 3.

- DCG@3 = 0/log₂(2) + 1/log₂(3) + 1/log₂(4) = 0 + 0.631 + 0.500 = **1.131**
- Ideal order [B, C, A]: IDCG@3 = 1/log₂(2) + 1/log₂(3) = 1.0 + 0.631 = **1.631**
- NDCG@3 = 1.131 / 1.631 = **0.693**

---

**Beyond accuracy — catalog-level metrics:**

| Metric | What it measures | Why it matters |
|---|---|---|
| **Coverage** | % of the item catalog that ever appears in recommendations | Low coverage = popularity bias |
| **Diversity** | Average pairwise dissimilarity among the recommended items | Prevents repetitive feeds |
| **Novelty** | Are recommendations items the user hasn't seen before? | Drives discovery |
| **Serendipity** | Surprising yet relevant recommendations | Prevents filter bubbles |

---

**Offline vs Online evaluation:**

Offline metrics (NDCG, Precision@K) measure on historical held-out data — fast and cheap. Good for rapid iteration.

Online metrics (CTR, watch time, purchases) measured via A/B tests — definitive but expensive and slow.

**Critical rule:** Offline NDCG improvement does NOT always translate to online CTR improvement. A model can score perfectly on past data but fail on live traffic due to distribution shift or feedback loops. Always validate with an A/B test before shipping.

## Q11: What is the explore-exploit trade-off in recommendations?

**Intuition:** A recommender that only shows items it's confident you like (exploitation) will narrow your feed into a filter bubble and never discover your new interests. But showing only unfamiliar items (exploration) gives a bad user experience. The ideal system does both.

**Exploitation:** Recommend items the model is confident the user will enjoy, based on proven history.

**Exploration:** Occasionally recommend items with uncertain appeal — to gather new signal and potentially discover new preferences.

**Why exploration matters:**
- The model only learns about items it has recommended — never recommending new items means never learning about them
- A newly released item has no data; pure exploitation never surfaces it
- User tastes evolve — a jazz fan might not listen to jazz in the morning; pure exploitation misses this

**Common approaches:**

**ε-greedy:** With probability ε show a random item; with probability 1−ε show the best predicted item. Simple, robust baseline.

**Upper Confidence Bound (UCB):** Score each item by (predicted score + exploration bonus proportional to uncertainty). Items rarely shown get a large bonus → natural exploration.

**Thompson Sampling:** Maintain a probability distribution over each item's expected reward. Sample from distributions and recommend highest sampled value. Uncertain items occasionally get sampled high → organic exploration.

**Production reality:** Most large platforms reserve 10–20% of feed slots explicitly for exploration — new releases, trending items in adjacent categories, items from under-represented creators.

## Q12: What is popularity bias and how do you handle it?

**Intuition:** Recommenders have a rich-get-richer problem. Popular items get many clicks → model sees more training data for them → model recommends them more → they get even more clicks. Niche items with passionate audiences never break through because they lack initial exposure.

**Why it happens:**
- Training data follows a power-law — the top 1% of items account for 50%+ of interactions
- The model over-indexes on popularity as an implicit feature
- Cold-start items never accumulate enough signal to rank highly

**How to detect it:**
- **Gini coefficient** of recommendation distribution: high Gini = concentrated on few items
- **Catalog coverage**: if only 5% of items ever appear in recommendations, popularity bias is severe
- Compare average popularity of recommended items vs. average popularity of all items

**Solutions:**

**1. Inverse popularity weighting during training:**
Down-weight popular items so the model doesn't over-optimize for them:
$$w_{ui} = \frac{1}{\text{pop}(i)^\alpha}, \quad \alpha \in [0, 0.5]$$

**2. Popularity-aware ranking:**
Subtract a popularity penalty from scores at ranking time. Penalize items that already appear in the top-N for more than X% of users.

**3. Coverage constraints:**
Hard rule: ensure at least Y% of recommended items come from the "long tail" (items with fewer than Z total interactions).

**4. Re-ranking for diversity:**
Post-processing step: re-rank the top-50 to ensure variety by category, popularity tier, and recency before returning the final top-10.

**5. Counterfactual debiasing:**
Model the probability that an item was shown (propensity) and down-weight interactions that happened only because the item was already popular. Inverse Propensity Scoring (IPS) corrects for exposure bias in the training signal.

**Trade-off:** De-biasing reduces short-term CTR (popular items are popular for a reason) but improves long-term user retention, catalog health, and creator ecosystem fairness. Frame it as a long-term value vs. short-term engagement decision.
