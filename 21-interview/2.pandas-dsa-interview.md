## Q1: What is the difference between a DataFrame and a Series?

**Series:** A one-dimensional labeled array — like a single column of a table, with an index.

```python
import pandas as pd

s = pd.Series([10, 20, 30], index=['a', 'b', 'c'])
# a    10
# b    20
# c    30
```

**DataFrame:** A two-dimensional labeled table. Each column is a Series sharing the same index.

```python
df = pd.DataFrame({
    'name':   ['Alice', 'Bob',   'Carol'],
    'salary': [90000,   75000,   110000],
    'dept':   ['Eng',   'Mkt',   'Eng']
})
```

| | name | salary | dept |
|---|---|---|---|
| 0 | Alice | 90000 | Eng |
| 1 | Bob | 75000 | Mkt |
| 2 | Carol | 110000 | Eng |

**Relationship:**
```python
df['salary']             # → Series (one column)
df[['salary', 'dept']]   # → DataFrame (two columns; double brackets)
df.shape                 # (3, 3) — (rows, cols)
df.dtypes                # dtype of each column
df.describe()            # summary stats for numeric columns
```

**Intuition:** A DataFrame is a dictionary of Series objects that all share the same row index. When you select one column, you get back a Series.

## Q2: What is the difference between `.loc` and `.iloc`?

Both select rows and columns, but use different addressing:

| | `.loc` | `.iloc` |
|---|---|---|
| **Addressing** | Label-based (index names, column names) | Integer position-based (0, 1, 2, …) |
| **Slice end** | **Inclusive** | **Exclusive** (like Python lists) |

```python
df = pd.DataFrame({
    'name':   ['Alice', 'Bob',  'Carol'],
    'salary': [90000,   75000,  110000]
}, index=['a', 'b', 'c'])

# .loc — use labels
df.loc['a']              # row with index label 'a'
df.loc['a':'b']          # rows 'a' and 'b' — INCLUSIVE of 'b'
df.loc['a', 'salary']    # scalar: 90000
df.loc[:, 'salary']      # all rows, salary column

# .iloc — use integer positions
df.iloc[0]               # first row (index label 'a')
df.iloc[0:2]             # rows 0 and 1 — EXCLUSIVE of 2 (NOT row 2)
df.iloc[0, 1]            # row 0, column at position 1 → 90000
df.iloc[:, 1]            # all rows, second column
```

**Classic gotcha:** If your index is integers (0, 1, 2):
- `df.loc[0:2]` → returns rows 0, 1, AND 2 (inclusive)
- `df.iloc[0:2]` → returns rows 0 and 1 only (exclusive)

They behave differently even for integer-labeled indexes.

**Boolean indexing (most common in practice — uses `.loc`):**
```python
df.loc[df['salary'] > 80000]                      # all high earners
df.loc[df['dept'] == 'Eng', 'salary']             # salaries of Eng employees only
df.loc[(df['dept'] == 'Eng') & (df['salary'] > 85000)]  # AND condition
```

**Rule of thumb:** Use `.iloc` for positional access (first N rows, loop indices). Use `.loc` for semantic access (filter by value, select by label).

## Q3: How do you handle missing values in pandas?

**Step 1 — Detect missing values:**
```python
df.isnull()                            # boolean DataFrame: True where NaN
df.isnull().sum()                      # count NaN per column
df.isnull().sum() / len(df) * 100      # percent missing per column
df.isnull().any(axis=1)                # True for any row that has at least one NaN
```

**Step 2 — Drop missing values:**
```python
df.dropna()                            # drop any row with at least one NaN
df.dropna(subset=['salary'])           # only drop rows where salary is NaN
df.dropna(thresh=3)                    # keep rows with at least 3 non-NaN values
df.dropna(axis=1)                      # drop any column with at least one NaN
```

**Step 3 — Fill missing values:**
```python
df['salary'].fillna(df['salary'].mean())       # fill with column mean
df['salary'].fillna(df['salary'].median())     # fill with median (robust to outliers)
df['dept'].fillna('Unknown')                   # fill categorical with a placeholder
df['price'].fillna(method='ffill')             # forward fill: use previous valid value
df['price'].fillna(method='bfill')             # backward fill: use next valid value
```

**Capture missingness as a feature:**
```python
# The fact that a value is missing can itself be informative
df['salary_was_missing'] = df['salary'].isnull().astype(int)
df['salary'] = df['salary'].fillna(df['salary'].median())
```

**Interpolation (for time series):**
```python
df['price'].interpolate(method='linear')       # estimate missing value from neighbors
df['price'].interpolate(method='time')         # time-aware interpolation
```

**Decision guide:**
- < 5% missing and random → mean/median fill is fine
- 5–20% missing → consider a missingness indicator + fill
- > 20% missing → the feature may be uninformative; consider dropping it
- Missingness is patterned (e.g., lab test not ordered = patient is healthy) → always capture as a binary indicator

## Q4: How does `groupby` work? What is the split-apply-combine pattern?

**Intuition:** `groupby` follows a three-step pattern:
1. **Split** — divide the DataFrame into groups based on a column
2. **Apply** — run a function on each group independently
3. **Combine** — stitch the results back into a single output

Input:

| | dept | salary | age |
|---|---|---|---|
| 0 | Eng | 90000 | 25 |
| 1 | Mkt | 75000 | 30 |
| 2 | Eng | 110000 | 35 |
| 3 | Mkt | 80000 | 28 |
| 4 | Eng | 95000 | 32 |

```python
df = pd.DataFrame({
    'dept':   ['Eng', 'Mkt', 'Eng', 'Mkt', 'Eng'],
    'salary': [90000, 75000, 110000, 80000, 95000],
    'age':    [25,    30,    35,     28,    32]
})

# Basic aggregation
df.groupby('dept')['salary'].mean()
# dept
# Eng    98333.3
# Mkt    77500.0

# Multiple functions at once
df.groupby('dept').agg({
    'salary': ['mean', 'max', 'count'],
    'age':    'median'
})

# Named aggregations (pandas ≥ 0.25)
df.groupby('dept').agg(
    avg_salary=('salary', 'mean'),
    max_salary=('salary', 'max'),
    headcount=('salary', 'count')
)

# Custom function via apply
df.groupby('dept')['salary'].apply(lambda x: x.max() - x.min())
# salary range per department
```

Output of `df.groupby('dept')['salary'].mean()`:

| dept | salary |
|---|---|
| Eng | 98333.3 |
| Mkt | 77500.0 |

Output of named aggregation:

| dept | avg_salary | max_salary | headcount |
|---|---|---|---|
| Eng | 98333.3 | 110000 | 3 |
| Mkt | 77500.0 | 80000 | 2 |

Output of `df.groupby('dept').agg({'salary': ['mean', 'max', 'count'], 'age': 'median'})`:

| dept | salary_mean | salary_max | salary_count | age_median |
|---|---|---|---|---|
| Eng | 98333.3 | 110000 | 3 | 32.0 |
| Mkt | 77500.0 | 80000 | 2 | 29.0 |

Output of salary range per department:

| dept | salary_range |
|---|---|
| Eng | 20000 |
| Mkt | 5000 |

**Common interview follow-up — flatten multi-index column names:**
```python
res = df.groupby('dept').agg({
    'salary': ['mean', 'max', 'count'],
    'age':    'median'
})

# Flatten column names
res.columns = [f"{col[0]}_{col[1]}" for col in res.columns]
res = res.reset_index()
```

Output after flattening and `reset_index()`:

| | dept | salary_mean | salary_max | salary_count | age_median |
|---|---|---|---|---|---|
| 0 | Eng | 98333.3 | 110000 | 3 | 32.0 |
| 1 | Mkt | 77500.0 | 80000 | 2 | 29.0 |

**transform — adds group stats as a new column (same shape as original):**
```python
# Add department average salary as a column next to each employee row
df['dept_avg'] = df.groupby('dept')['salary'].transform('mean')

# Add each employee's salary as a fraction of their department average
df['salary_vs_dept'] = df['salary'] / df.groupby('dept')['salary'].transform('mean')
```

Output after `transform`:

| | dept | salary | age | dept_avg | salary_vs_dept |
|---|---|---|---|---|---|
| 0 | Eng | 90000 | 25 | 98333.3 | 0.92 |
| 1 | Mkt | 75000 | 30 | 77500.0 | 0.97 |
| 2 | Eng | 110000 | 35 | 98333.3 | 1.12 |
| 3 | Mkt | 80000 | 28 | 77500.0 | 1.03 |
| 4 | Eng | 95000 | 32 | 98333.3 | 0.97 |

**groupby + multiple columns:**
```python
df.groupby(['dept', 'level'])['salary'].mean()   # multi-level index result
df.groupby(['dept', 'level']).agg({'salary': 'mean'}).reset_index()  # flat result
```

## Q5: What is the difference between `merge`, `join`, and `concat`?

All three combine DataFrames but in different ways:

**`pd.concat`** — Stack DataFrames by rows or columns (no key matching):
```python
# Append rows (like SQL UNION ALL)
pd.concat([df1, df2], axis=0, ignore_index=True)

# Place DataFrames side by side (axis=1)
pd.concat([df1, df2], axis=1)
```
Use when: combining DataFrames with the same schema, or adding feature columns.

**`pd.merge`** — Join on a common column (like SQL JOIN):
```python
# Equivalent to: SELECT * FROM employees JOIN departments ON employees.dept_id = departments.dept_id
pd.merge(employees, departments, on='dept_id', how='inner')

# Different column names in each table
pd.merge(employees, departments, left_on='dept_id', right_on='id', how='left')

# Merge on multiple keys
pd.merge(df1, df2, on=['user_id', 'date'], how='inner')

# how: 'inner', 'left', 'right', 'outer' — same semantics as SQL JOINs
```
Use when: combining DataFrames on a meaningful shared key column.

**`df.join`** — Shortcut for merging on the DataFrame index:
```python
# Both DataFrames must have the same index (e.g., user_id as index)
df1.join(df2, how='left')
```
Use when: both DataFrames are already indexed by the same key.

**Quick reference:**
| | When to use |
|---|---|
| `concat` | Stacking rows (appending data) or columns (adding features) |
| `merge` | SQL-style JOIN on any key column — most explicit and general |
| `join` | Quick join when both DataFrames share the same index |

## Q6: How do you apply a function to a DataFrame? (`apply`, `map`, vectorized ops)

**Vectorized operations — always prefer these (fastest, uses NumPy under the hood):**
```python
df['salary'] * 1.1                         # 10% raise for everyone
df['salary'] / df['age']                   # salary per year of age
df['name'].str.upper()                     # string vectorized ops
(df['salary'] > 80000).astype(int)         # boolean → integer column
```

**`Series.map`** — element-wise on a single Series (recode values or apply a function):
```python
df['dept'].map({'Eng': 'Engineering', 'Mkt': 'Marketing'})   # dictionary lookup
df['salary'].map(lambda x: round(x, -3))                     # round to nearest 1000
```
Note: `map` with a dict silently converts unmatched values to NaN — use `.fillna` after if needed.

**`DataFrame.apply`** — apply a function along an axis (row or column):
```python
# Along columns (axis=0, default) — function receives each column as a Series
df.apply(lambda col: col.max() - col.min())   # value range per column

# Along rows (axis=1) — function receives each row as a Series
df.apply(lambda row: row['salary'] * 1.1 if row['dept'] == 'Eng' else row['salary'], axis=1)
```

**`apply` vs vectorized — performance reality:**
```python
# Slow: Python loop via apply (avoids NumPy)
df['salary'].apply(lambda x: x * 1.1)   # ~10x slower on large DataFrames

# Fast: vectorized (NumPy C loop)
df['salary'] * 1.1
```

**Rule:** Try vectorized first (arithmetic, string methods, `.where`, `.clip`). Use `.map` for simple element-wise recoding. Use `.apply` for complex multi-column or conditional logic that can't be vectorized. Avoid `.applymap` on large DataFrames — it's the slowest option.

## Q7: What is the difference between a pandas copy and a view?

**View:** A DataFrame that references the SAME underlying data as the original. Modifying the view may modify the original — this is the source of the infamous `SettingWithCopyWarning`.

**Copy:** A completely independent DataFrame with its own data. Modifying it never touches the original.

```python
df = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5, 6]})

# This MAY be a view (pandas decides internally based on operation type)
subset = df[df['a'] > 1]
subset['b'] = 99   # SettingWithCopyWarning! — may or may not change df

# Explicit copy — always safe
subset = df[df['a'] > 1].copy()
subset['b'] = 99   # guaranteed: df is unchanged
```

**Common bug pattern:**
```python
high_earners = df[df['salary'] > 80000]
high_earners['bonus'] = high_earners['salary'] * 0.1   # SettingWithCopyWarning!

# Fix:
high_earners = df[df['salary'] > 80000].copy()
high_earners['bonus'] = high_earners['salary'] * 0.1   # safe
```

**In pandas 2.0+ Copy-on-Write:** pandas 2.0 introduces Copy-on-Write semantics — modifying any subset always produces an independent copy, eliminating this class of bugs. But `.copy()` still makes intent explicit and is backward-compatible.

**Rule:** Always call `.copy()` when you plan to modify a filtered subset. The cost is minimal; the protection is complete.

## Q8: How do you filter rows in a DataFrame efficiently?

**Most common interview pattern:** build a boolean mask, then pass it to `.loc[...]`. This is explicit, composable, and easy to debug.

```python
df = pd.DataFrame({
    'name':   ['Alice', 'Bob', 'Carol', 'Dave'],
    'dept':   ['Eng', 'Mkt', 'Eng', 'Sales'],
    'salary': [120000, 75000, 95000, 68000],
    'city':   ['BLR', 'SF', 'BLR', 'NYC']
})

df.loc[df['salary'] > 80000]
```

Output:

| | name | dept | salary | city |
|---|---|---|---|---|
| 0 | Alice | Eng | 120000 | BLR |
| 2 | Carol | Eng | 95000 | BLR |

**Common filters:**
```python
df.loc[df['dept'] == 'Eng']                          # equality
df.loc[df['dept'].isin(['Eng', 'Sales'])]           # membership
df.loc[df['salary'].between(70000, 100000)]         # range inclusive
df.loc[df['city'].ne('BLR')]                        # not equal
df.loc[df['dept'].eq('Eng') & df['salary'].gt(90000)]   # AND
df.loc[df['dept'].eq('Eng') | df['city'].eq('NYC')]     # OR
df.loc[df['city'].isna()]                           # missing values
```

**Combined-condition example:**
```python
df.loc[(df['dept'] == 'Eng') & (df['salary'] >= 95000), ['name', 'salary']]
```

Output:

| | name | salary |
|---|---|---|
| 0 | Alice | 120000 |
| 2 | Carol | 95000 |

**`query` syntax** can be faster to write in interviews:
```python
df.query("dept == 'Eng' and salary >= 95000")[['name', 'salary']]
```

**Rule:** Use `.loc[mask, cols]` in production code and interviews. It is clearer than chained indexing like `df[df['salary'] > 80000]['name']`.

## Q9: What is the difference between `agg`, `transform`, and `filter` in pandas groupby?

These three are constantly confused. The difference is the output shape:

| Method | Returns | Best use |
|---|---|---|
| `agg` | One row per group | Summaries like mean, max, count |
| `transform` | Same number of rows as input | Add group-derived values back to each row |
| `filter` | Subset of original rows | Keep or drop whole groups based on a condition |

**Pandas vs SQL for aggregation and window-style operations:**

| Pandas code | Full SQL query | Output shape | When to use |
|---|---|---|---|
| <code>df.groupby('dept').agg(avg_salary=('salary', 'mean'), headcount=('salary', 'size'))</code> | <code>SELECT dept, AVG(salary) AS avg_salary, COUNT(*) AS headcount FROM employees GROUP BY dept;</code> | One row per group | Group-level summary table |
| <code>df['dept_avg'] = df.groupby('dept')['salary'].transform('mean')</code><br><code>df['vs_dept_avg'] = df['salary'] - df['dept_avg']</code> | <code>SELECT dept, salary, AVG(salary) OVER (PARTITION BY dept) AS dept_avg, salary - AVG(salary) OVER (PARTITION BY dept) AS vs_dept_avg FROM employees;</code> | Same rows as input | Add per-group stats back to each row |
| <code>df.groupby('dept').filter(lambda g: len(g) &gt;= 2)</code> | <code>WITH counts AS ( SELECT dept, salary, COUNT(*) OVER (PARTITION BY dept) AS dept_count FROM employees ) SELECT dept, salary FROM counts WHERE dept_count &gt;= 2;</code> | Subset of original rows | Keep or drop whole groups based on a rule |
| <code>df['prev_sales'] = df.groupby('user_id')['sales'].shift(1)</code> | <code>SELECT user_id, date, sales, LAG(sales, 1) OVER (PARTITION BY user_id ORDER BY date) AS prev_sales FROM sales_data;</code> | Same rows as input | Previous-row value within each group |
| <code>df['running_sales'] = df.groupby('user_id')['sales'].cumsum()</code> | <code>SELECT user_id, date, sales, SUM(sales) OVER (PARTITION BY user_id ORDER BY date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_sales FROM sales_data;</code> | Same rows as input | Running totals |
| <code>df['rank_in_user'] = df.groupby('user_id')['sales'].rank(method='dense', ascending=False)</code> | <code>SELECT user_id, date, sales, DENSE_RANK() OVER (PARTITION BY user_id ORDER BY sales DESC) AS rank_in_user FROM sales_data;</code> | Same rows as input | Rank rows within each group |
| <code>df['rolling_2d_avg'] = df.groupby('user_id')['sales'].transform(lambda s: s.rolling(2, min_periods=1).mean())</code> | <code>SELECT user_id, date, sales, AVG(sales) OVER (PARTITION BY user_id ORDER BY date ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS rolling_2d_avg FROM sales_data;</code> | Same rows as input | Rolling or moving metrics |
| <code>df.pivot_table(index='dept', columns='city', values='sales', aggfunc='mean', fill_value=0)</code> | <code>SELECT dept, COALESCE(AVG(CASE WHEN city = 'BLR' THEN sales END), 0) AS BLR, COALESCE(AVG(CASE WHEN city = 'SF' THEN sales END), 0) AS SF FROM sales GROUP BY dept;</code> | One row per index value | Spreadsheet-style summary matrix |
| <code>pd.crosstab(df['dept'], df['city'])</code> | <code>SELECT dept, SUM(CASE WHEN city = 'BLR' THEN 1 ELSE 0 END) AS BLR, SUM(CASE WHEN city = 'SF' THEN 1 ELSE 0 END) AS SF FROM sales GROUP BY dept;</code> | One row per index value | Frequency table |

**Rule of thumb:** if pandas reduces rows, think `GROUP BY`. If pandas preserves rows and adds context columns, think window function. If pandas reshapes into a matrix, think grouped conditional aggregation.

```python
df = pd.DataFrame({
    'dept':   ['Eng', 'Eng', 'Mkt', 'Mkt', 'Sales'],
    'salary': [120000, 95000, 70000, 80000, 68000]
})
```

**`agg` example:**
```python
df.groupby('dept').agg(avg_salary=('salary', 'mean'), headcount=('salary', 'size'))
```

Output:

| dept | avg_salary | headcount |
|---|---|---|
| Eng | 107500.0 | 2 |
| Mkt | 75000.0 | 2 |
| Sales | 68000.0 | 1 |

**`transform` example:**
```python
df['dept_avg'] = df.groupby('dept')['salary'].transform('mean')
df['vs_dept_avg'] = df['salary'] - df['dept_avg']
df
```

Output:

| | dept | salary | dept_avg | vs_dept_avg |
|---|---|---|---|---|
| 0 | Eng | 120000 | 107500.0 | 12500.0 |
| 1 | Eng | 95000 | 107500.0 | -12500.0 |
| 2 | Mkt | 70000 | 75000.0 | -5000.0 |
| 3 | Mkt | 80000 | 75000.0 | 5000.0 |
| 4 | Sales | 68000 | 68000.0 | 0.0 |

**`filter` example:**
```python
df.groupby('dept').filter(lambda g: len(g) >= 2)
```

Output:

| | dept | salary |
|---|---|---|
| 0 | Eng | 120000 |
| 1 | Eng | 95000 |
| 2 | Mkt | 70000 |
| 3 | Mkt | 80000 |

**Interview answer:** `agg` reduces, `transform` broadcasts, `filter` keeps or drops entire groups.

## Q10: How do window-style transforms work in pandas?

Window-style operations compute a value from nearby rows while preserving row-level granularity. In pandas interviews, this usually means `shift`, cumulative functions, or `rolling` combined with `groupby`.

```python
df = pd.DataFrame({
    'user_id': [1, 1, 1, 2, 2],
    'date':    pd.to_datetime(['2025-01-01', '2025-01-02', '2025-01-03', '2025-01-01', '2025-01-02']),
    'sales':   [10, 15, 7, 20, 25]
}).sort_values(['user_id', 'date'])

df['prev_sales'] = df.groupby('user_id')['sales'].shift(1)
df['running_sales'] = df.groupby('user_id')['sales'].cumsum()
df['rolling_2d_avg'] = (
    df.groupby('user_id')['sales']
      .transform(lambda s: s.rolling(2, min_periods=1).mean())
)
df
```

Output:

| | user_id | date | sales | prev_sales | running_sales | rolling_2d_avg |
|---|---|---|---|---|---|---|
| 0 | 1 | 2025-01-01 | 10 | NaN | 10 | 10.0 |
| 1 | 1 | 2025-01-02 | 15 | 10.0 | 25 | 12.5 |
| 2 | 1 | 2025-01-03 | 7 | 15.0 | 32 | 11.0 |
| 3 | 2 | 2025-01-01 | 20 | NaN | 20 | 20.0 |
| 4 | 2 | 2025-01-02 | 25 | 20.0 | 45 | 22.5 |

**Other frequently asked patterns:**
```python
df['rank_in_user'] = df.groupby('user_id')['sales'].rank(method='dense', ascending=False)
df['pct_change'] = df.groupby('user_id')['sales'].pct_change()
```

Output:

| | user_id | date | sales | rank_in_user | pct_change |
|---|---|---|---|---|---|
| 0 | 1 | 2025-01-01 | 10 | 2.0 | NaN |
| 1 | 1 | 2025-01-02 | 15 | 1.0 | 0.50 |
| 2 | 1 | 2025-01-03 | 7 | 3.0 | -0.53 |
| 3 | 2 | 2025-01-01 | 20 | 2.0 | NaN |
| 4 | 2 | 2025-01-02 | 25 | 1.0 | 0.25 |

**Rule:** `agg` collapses rows. Window transforms like `shift`, `cumsum`, `rank`, and `rolling(...).mean()` keep rows and add context columns.

## Q11: What is the difference between `pivot`, `pivot_table`, and `crosstab`?

All three reshape data, but they solve different interview problems:

| Method | Use case | Handles duplicates? | Aggregation? |
|---|---|---|---|
| `pivot` | Pure reshape | No | No |
| `pivot_table` | Spreadsheet-style summary | Yes | Yes |
| `pd.crosstab` | Frequency table | Yes | Counts by default |

```python
df = pd.DataFrame({
    'dept':  ['Eng', 'Eng', 'Mkt', 'Mkt', 'Mkt'],
    'city':  ['BLR', 'SF', 'BLR', 'SF', 'SF'],
    'sales': [100, 120, 80, 90, 110]
})
```

**`pivot` example** works only if each `(dept, city)` pair is unique:
```python
unique_df = df.drop_duplicates(['dept', 'city'], keep='first')
unique_df.pivot(index='dept', columns='city', values='sales')
```

Output:

| dept | BLR | SF |
|---|---|---|
| Eng | 100 | 120 |
| Mkt | 80 | 90 |

**`pivot_table` example** handles duplicate `Mkt-SF` rows by aggregating:
```python
df.pivot_table(index='dept', columns='city', values='sales', aggfunc='mean', fill_value=0)
```

Output:

| dept | BLR | SF |
|---|---|---|
| Eng | 100 | 120 |
| Mkt | 80 | 100 |

**`crosstab` example** counts combinations:
```python
pd.crosstab(df['dept'], df['city'])
```

Output:

| dept | BLR | SF |
|---|---|---|
| Eng | 1 | 1 |
| Mkt | 1 | 2 |

**Interview answer:** use `pivot` when keys are unique, `pivot_table` when duplicates need aggregation, and `crosstab` for count matrices.

## Q12: Why is NumPy faster than pure Python lists for numerical work?

**Core answer:** NumPy arrays are homogeneous, contiguous blocks of memory and their operations run in optimized C loops. Python lists store pointers to Python objects, so each arithmetic step has much higher overhead.

```python
import numpy as np

arr = np.array([1, 2, 3, 4])
arr * 10
```

Output:

| index | value |
|---|---|
| 0 | 10 |
| 1 | 20 |
| 2 | 30 |
| 3 | 40 |

**Why lists are slower:**
```python
[x * 10 for x in [1, 2, 3, 4]]
```

Output:

| index | value |
|---|---|
| 0 | 10 |
| 1 | 20 |
| 2 | 30 |
| 3 | 40 |

The output is the same, but NumPy avoids Python-level looping and scales much better on large arrays.

**Interview soundbite:** NumPy is fast because it stores same-type values densely in memory and pushes the loop into compiled code.

## Q13: What is broadcasting in NumPy?

Broadcasting lets NumPy apply arithmetic between arrays of different but compatible shapes without manually copying data.

```python
import numpy as np

X = np.array([
    [1, 2, 3],
    [4, 5, 6]

bias = np.array([10, 20, 30])

X + bias
```

Output:

| | 0 | 1 | 2 |
|---|---|---|---|
| 0 | 11 | 22 | 33 |
| 1 | 14 | 25 | 36 |

NumPy treats `bias` as if it were copied across each row:

```python
np.array([
    [10, 20, 30],
    [10, 20, 30]
])
```

**Another common example:**
```python
X.mean(axis=0)
```

Output:

| index | mean |
|---|---|
| 0 | 2.5 |
| 1 | 3.5 |
| 2 | 4.5 |

**Interview answer:** broadcasting expands dimensions conceptually, not physically, as long as trailing dimensions match or one side is 1.

## Q14: What is the difference between NumPy views and copies?

This is one of the highest-signal NumPy questions because it affects both correctness and memory usage.

**Slicing usually returns a view** — it shares memory with the original array.

```python
import numpy as np

arr = np.array([10, 20, 30, 40])
view = arr[1:3]
view[0] = 999
arr
```

Output:

| index | value |
|---|---|
| 0 | 10 |
| 1 | 999 |
| 2 | 30 |
| 3 | 40 |

Because `view` shares memory, editing `view` changed `arr`.

**Fancy indexing returns a copy** — it does not share memory.

```python
arr = np.array([10, 20, 30, 40])
copy_arr = arr[[1, 3]]
copy_arr[0] = 999
arr
```

Output:

| index | value |
|---|---|
| 0 | 10 |
| 1 | 20 |
| 2 | 30 |
| 3 | 40 |

**Rule:** plain slicing like `arr[1:3]` is usually a view; boolean or integer array indexing usually makes a copy.

## Q15: What is Big O notation? Time complexities of common Python data structures.

**Big O** describes how runtime grows relative to input size n, ignoring constant factors and lower-order terms.

**Common complexities (best to worst):**

| Notation | Name | Example |
|---|---|---|
| O(1) | Constant | dict lookup, list append to end |
| O(log n) | Logarithmic | binary search in sorted array |
| O(n) | Linear | scan every element once |
| O(n log n) | Linearithmic | sorting (Python's Timsort, merge sort) |
| O(n²) | Quadratic | nested loops over n elements |
| O(2ⁿ) | Exponential | naive Fibonacci recursion |

**Python data structure complexities:**

| Operation | `list` | `dict` / `set` | `heapq` |
|---|---|---|---|
| Access by index | O(1) | — | — |
| Search / in-check | **O(n)** | **O(1)** avg | O(n) |
| Insert at end | O(1) amortized | O(1) avg | O(log n) |
| Insert at front | **O(n)** | O(1) | — |
| Delete by value | O(n) | O(1) avg | O(log n) |
| Min / Max | O(n) | O(n) | **O(1)** |

**Key practical insight:**
```python
# Searching in a list is O(n) — slow in a hot loop
if user_id in flagged_users_list:   # scans entire list

# Converting to a set makes lookup O(1)
flagged_set = set(flagged_users_list)
if user_id in flagged_set:          # hash lookup — constant time
```

**For ML pipelines:** Choosing the right data structure at the feature engineering step often matters more than algorithm choice. A dict-based lookup table instead of a repeated dataframe filter can cut pipeline time significantly.

## Q16: What is a hash map and why is it O(1) lookup?

**Intuition:** A hash map (Python `dict`) is like a filing cabinet with labeled drawers. Instead of searching every drawer, you compute which drawer a key belongs to using a hash function — one computation, one lookup.

**How it works:**
1. Compute `bucket = hash(key) % num_buckets` — maps any key to an integer bucket index
2. Store the `(key, value)` pair in that bucket
3. On lookup: compute the same hash → go directly to that bucket → return value

```python
# Python dict is a hash map
freq = {}
for word in words:
    freq[word] = freq.get(word, 0) + 1   # O(1) per word

# collections.Counter does the same
from collections import Counter
Counter(['a', 'b', 'a', 'c', 'b', 'a'])
# Counter({'a': 3, 'b': 2, 'c': 1})
```

**Classic interview problem — Two Sum (shows the hash map pattern):**
```python
def two_sum(nums, target):
    seen = {}                           # value → index
    for i, n in enumerate(nums):
        complement = target - n
        if complement in seen:          # O(1) lookup
            return [seen[complement], i]
        seen[n] = i
# O(n) total — vs O(n²) with nested loops
```

**Other common patterns:**
```python
# Grouping (like a manual groupby)
from collections import defaultdict
groups = defaultdict(list)
for item in data:
    groups[item['category']].append(item)

# LRU cache / memoization
from functools import lru_cache
@lru_cache(maxsize=128)
def expensive(n): ...
```

**Hash collision:** Two different keys can hash to the same bucket. Python handles this with open addressing (probing nearby buckets). Average case remains O(1); worst case is O(n) but practically rare.

## Q17: What is binary search and when do you use it?

**Intuition:** Searching a sorted phone book — you don't start from page 1. You open the middle, decide which half to search, and cut the space in half each step. Binary search does exactly this, requiring **O(log n)** comparisons instead of O(n).

**Requirement:** The array must be sorted. Binary search on an unsorted array is incorrect.

**Algorithm:**
```python
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid           # found at index mid
        elif arr[mid] < target:
            lo = mid + 1         # target is in the right half
        else:
            hi = mid - 1         # target is in the left half
    return -1                    # not found

# Example: arr = [1, 3, 5, 7, 9], target = 7
# Iteration 1: mid=2, arr[2]=5 < 7 → lo=3
# Iteration 2: mid=3, arr[3]=7 == 7 → return 3
```

**Python's `bisect` module (use this in production):**
```python
import bisect
arr = [10, 20, 30, 40, 50]

bisect.bisect_left(arr, 30)    # 2 — leftmost position where 30 can be inserted
bisect.bisect_right(arr, 30)   # 3 — rightmost position
bisect.insort(arr, 25)         # insert 25 in sorted position: [10, 20, 25, 30, 40, 50]
```

**Complexity:** O(log n). For n = 1,000,000 → at most 20 iterations.

**When to use binary search in DS/ML work:**
- Finding the optimal threshold for a classifier (e.g., "find the threshold where precision = 0.9")
- Searching a sorted list of feature values for a decision tree split point
- `bisect.insort` to maintain a sorted running list during streaming feature computation

## Q18: What is the sliding window technique?

**Intuition:** When analyzing a contiguous subarray, instead of recomputing from scratch each step, slide the window by adding one element on the right and removing one on the left. Update the running result incrementally → O(n) instead of O(n×k).

**Fixed-size window — max sum of K consecutive elements:**
```python
def max_sum_window(arr, k):
    window_sum = sum(arr[:k])    # compute the first window
    max_sum = window_sum

    for i in range(k, len(arr)):
        window_sum += arr[i] - arr[i - k]   # slide: add new element, drop old
        max_sum = max(max_sum, window_sum)

    return max_sum

# arr = [2, 1, 5, 1, 3, 2], k = 3
# windows: [2,1,5]=8, [1,5,1]=7, [5,1,3]=9, [1,3,2]=6  → max = 9
```
Brute force would recompute each window sum: O(n × k). Sliding window: O(n).

**Variable-size window — longest substring without repeating characters:**
```python
def longest_unique_substring(s):
    seen = {}        # char → last seen index
    lo = 0           # left edge of window
    max_len = 0

    for hi, char in enumerate(s):
        if char in seen and seen[char] >= lo:
            lo = seen[char] + 1   # shrink window: push left edge past the duplicate
        seen[char] = hi
        max_len = max(max_len, hi - lo + 1)

    return max_len

# "abcabcbb" → 3 ("abc")
```

**When to use sliding window:**
- "Max/min/sum of any subarray of exactly size K"
- "Longest/shortest subarray satisfying condition X"
- Any problem involving a contiguous window over a sequence

**DS/ML connection:** Rolling window features in time series (7-day moving average, rolling standard deviation) are the data engineering version of this technique. `df['value'].rolling(7).mean()` in pandas implements exactly a sliding window.

## Q19: What is the two-pointer technique?

**Intuition:** Two pointers move through an array — usually from opposite ends or at different speeds — to avoid nested loops. Turns O(n²) into O(n).

**Classic — find a pair summing to target in a SORTED array:**
```python
def has_pair_sum(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo < hi:
        s = arr[lo] + arr[hi]
        if s == target:
            return True
        elif s < target:
            lo += 1    # sum too small → move left pointer right (increase sum)
        else:
            hi -= 1    # sum too large → move right pointer left (decrease sum)
    return False

# [1, 3, 5, 7, 9], target=10  →  3+7=10 → True
```
Brute force: check all pairs → O(n²). Two pointers: one pass → O(n).

**Removing duplicates from a sorted array in-place:**
```python
def remove_duplicates(nums):
    if not nums: return 0
    slow = 0
    for fast in range(1, len(nums)):
        if nums[fast] != nums[slow]:
            slow += 1
            nums[slow] = nums[fast]
    return slow + 1   # length of unique portion
```

**Fast/slow pointer — detect a cycle in a linked list:**
```python
def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next         # advances 1 step
        fast = fast.next.next    # advances 2 steps
        if slow is fast:
            return True          # they meet → cycle exists
    return False
```

**When to use two pointers:**
- Sorted array: pairs/triplets summing to a target
- Partition problems (move negatives to one side)
- Remove duplicates in-place
- Palindrome check

## Q20: What is the difference between BFS and DFS?

Both traverse every node in a graph or tree. They differ in the order visited.

**BFS (Breadth-First Search):** Visit all neighbors at the current level before going deeper. Uses a **queue (FIFO)**.

**DFS (Depth-First Search):** Go as deep as possible down one path before backtracking. Uses a **stack / recursion (LIFO)**.

```python
from collections import deque

def bfs(graph, start):
    visited = set([start])
    queue = deque([start])
    order = []
    while queue:
        node = queue.popleft()     # FIFO: process oldest (shallowest) first
        order.append(node)
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)
    return order

def dfs(graph, start, visited=None):
    if visited is None: visited = set()
    visited.add(start)
    result = [start]
    for neighbor in graph[start]:
        if neighbor not in visited:
            result += dfs(graph, neighbor, visited)
    return result
```

**When to use each:**

| Use case | Algorithm | Why |
|---|---|---|
| Shortest path (unweighted graph) | **BFS** | BFS always finds the fewest-edge path first |
| Level-order tree traversal | **BFS** | Processes level by level naturally |
| All paths / connected components | **DFS** | Simpler recursion |
| Cycle detection | DFS | Back-edge detection during DFS |
| Topological sort (DAG) | DFS | Post-order DFS gives reverse topological order |

**Complexity:** Both O(V + E) where V = number of vertices, E = number of edges.

**DS/ML connection:** Dependency resolution in ML pipelines (DAG of feature transformations) uses topological sort. Graph neural networks use neighborhood aggregation — conceptually related to BFS.

## Q21: What is dynamic programming? When do you use it?

**Intuition:** Dynamic programming (DP) solves a problem by breaking it into overlapping subproblems and caching each result so it's computed only once. It trades extra memory for dramatically better time complexity.

**Two signals that DP might be the right approach:**
1. The problem can be broken into subproblems of the same type (optimal substructure)
2. The same subproblems appear multiple times (overlapping subproblems)

**Example — Fibonacci without DP (exponential time O(2ⁿ)):**
```python
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)
# fib(40) recomputes fib(20) over a million times — extremely slow
```

**Top-down DP (memoization) — cache results as you recurse:**
```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)   # each value computed exactly once → O(n)
```

**Bottom-up DP (tabulation) — build up from base cases:**
```python
def fib(n):
    dp = [0] * (n + 1)
    dp[1] = 1
    for i in range(2, n + 1):
        dp[i] = dp[i-1] + dp[i-2]
    return dp[n]   # O(n) time, O(n) space
```

**Space-optimized (only keep last two values):**
```python
def fib(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a   # O(n) time, O(1) space
```

**Common DP patterns:**

| Pattern | Example problem | State |
|---|---|---|
| 1D DP | Climbing stairs, max stock profit | `dp[i]` |
| 2D DP | Longest common subsequence, edit distance | `dp[i][j]` |
| 0/1 Knapsack | Max value within weight limit | `dp[i][w]` |
| Interval DP | Burst balloons, matrix chain multiplication | `dp[i][j]` |

**Worked example — coin change (minimum number of coins for amount n):**
```python
def coin_change(coins, amount):
    dp = [float('inf')] * (amount + 1)
    dp[0] = 0   # base case: 0 coins needed for amount 0
    for amt in range(1, amount + 1):
        for coin in coins:
            if coin <= amt:
                dp[amt] = min(dp[amt], dp[amt - coin] + 1)
    return dp[amount] if dp[amount] != float('inf') else -1

coin_change([1, 5, 10, 25], 36)   # → 3 coins: 25 + 10 + 1
```

**DS/ML connections:**
- Viterbi algorithm (HMM decoding in NLP/speech) — DP over sequences
- Edit distance / Levenshtein distance — used as a string similarity feature
- Optimal tree splitting in decision trees
- Sequence alignment in bioinformatics feature engineering
