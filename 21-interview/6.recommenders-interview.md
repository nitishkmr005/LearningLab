## Q1: What are recommender systems and what are the main types?

**Intuition:** A recommender system answers the question "what will this specific user want next?" by learning patterns from the history of what many users have liked, clicked, bought, or watched. Think of it as a personalized matchmaker between users and items at scale.

**Three main families:**

**1. Collaborative Filtering (CF)**
"Users who behaved like you also liked these items."
- Uses only user-item interaction data (ratings, clicks, purchases)
- No item content needed — the pattern emerges from collective behavior
- Examples: Netflix "Because you watched X", Amazon "Customers also bought"

**2. Content-Based Filtering**
"Show you more items similar to what you already liked."
- Uses item features (genre, keywords, audio properties, embeddings)
- Builds a user profile from their past liked items and matches it to new items
- Works for a single user in isolation — doesn't need data from others
- Examples: Pandora's music genome, news article recommendations by topic

**3. Hybrid Systems**
Combine CF + content-based to get benefits of both.
Most production systems (Netflix, Spotify, YouTube, TikTok) are hybrid.

| | Collaborative Filtering | Content-Based |
|---|---|---|
| **Data needed** | User-item interactions | Item features |
| **New user cold start** | Problem — no history | OK — use item features |
| **New item cold start** | Problem — no ratings yet | OK — use item content |
| **Serendipity** | High — discovers unexpected items | Low — tends toward filter bubble |
| **Production default** | Yes — matrix factorization / two-tower | Yes — fallback for cold start |

## Q2: How is training data prepared for a recommender system?

**Intuition:** The training data is a table of "who interacted with what, when, and how strongly." The central challenge is extreme sparsity — a user on Netflix has watched maybe 200 out of 10 million titles (99.998% of interactions are missing).

**Step 1 — Build the user-item interaction matrix**

The core data structure: rows = users, columns = items, cells = interaction signal.

| | Movie A | Movie B | Movie C | Movie D |
|---|---|---|---|---|
| User 1 | 5.0 | — | 3.0 | — |
| User 2 | — | 4.0 | — | 2.0 |
| User 3 | 4.5 | — | — | 5.0 |

Most cells are empty (user hasn't seen the item). A 100M-user × 10M-item platform has 99.9%+ sparsity.

**Step 2 — Collect interaction signals**

| Signal type | Examples | Quality |
|---|---|---|
| Explicit feedback | Star ratings (1–5), thumbs up/down | High quality, low volume |
| Implicit feedback | Clicks, purchases, watch time, add-to-cart, replays, search | Noisy, but very high volume |

Most production systems rely on implicit feedback — users rarely rate things, but they click and watch constantly.

**Step 3 — Convert implicit signals into training labels**

```
Positive sample:  user purchased item          → label = 1
Negative sample:  item shown but not clicked   → label = 0 (weak negative)
Watch threshold:  watched > 70% of video       → positive
                  watched < 5% of video        → negative
```

**Step 4 — Negative sampling (critical)**

The matrix has mostly zeros. Training on ALL zeros as negatives would teach the model to predict zero everywhere. Fix:
- **Random negative sampling:** for each positive, randomly sample K items the user didn't interact with as negatives. Typical ratio: 1 positive to 4–10 negatives.
- **Hard negative sampling:** sample items the user was exposed to but ignored (harder = better training signal)
- **Popularity-weighted negatives:** sample negatives proportional to item popularity so the model learns to distinguish genuine interest from just popular items

**Step 5 — Augment with features**

Each (user, item) training pair gets enriched:

| Feature type | Examples |
|---|---|
| User features | Account age, device, location, genre preferences, recent history embedding |
| Item features | Genre, release year, language, popularity, content embedding |
| Context features | Time of day, day of week, current session length, referral source |

**Step 6 — Temporal train/eval split**

Always split by time, not randomly:
- Train: all interactions before date T
- Validation: interactions in [T, T+7 days]
- Test: interactions after T+7 days

Random split leaks future interactions into training — the model would "know" that User 1 liked Movie A even though that happened after deployment. This is a form of data leakage.

## Q3: What is collaborative filtering? User-based vs item-based?

**Intuition:** Collaborative filtering is the "wisdom of the crowd" approach. You don't need to know anything about the items themselves — you just need to observe that people with similar behavior tend to like the same things.

**User-based CF:** "Find users similar to you → recommend what they liked."

1. Compute similarity between User A and every other user (cosine similarity or Pearson correlation on their rating vectors)
2. Find the K nearest neighbors (most similar users)
3. Aggregate what those neighbors liked that User A hasn't seen
4. Recommend the top-scored unseen items

**Example:**
- User 1 liked: Inception, Interstellar, Tenet
- User 2 liked: Inception, Interstellar, The Prestige (very similar to User 1)
- User 1 hasn't seen The Prestige → recommend it

**Item-based CF:** "Find items similar to items you've liked → recommend those."

1. Compute similarity between every pair of items (using the column vectors of user ratings)
2. For each item User A liked, find its K most similar items
3. Recommend the top similar items User A hasn't seen

**Example:**
- Inception and Interstellar have similar rating vectors (the same users gave both high ratings)
- User 1 loved Inception → recommend Interstellar

**User-based vs Item-based:**

| | User-based | Item-based |
|---|---|---|
| **Intuition** | "People like you" | "Items like this" |
| **Stability** | User tastes shift over time | Item similarities are more stable |
| **Scalability** | Expensive — comparing billions of users | Better — item × item, fewer items than users |
| **Production use** | Rare at large scale | Common (Amazon's original CF was item-based) |

**Shared limitation:** As the platform grows, computing all pairwise similarities becomes O(n²) and prohibitively expensive. This is why matrix factorization and two-tower deep learning models replaced neighborhood-based CF at scale.

## Q4: What is content-based filtering?

**Intuition:** Instead of asking "who else liked this?", content-based filtering asks "what properties does this item have, and what properties has this user shown preference for?" It then matches the two profiles.

**How it works — step by step:**

**Step 1 — Build item profiles**
Represent each item as a feature vector:
- Movie: [genre_action=1, genre_drama=0, director_nolan=1, year=2010, ...]
- Article: TF-IDF vector over its words, or BERT sentence embedding
- Music track: tempo=128, energy=0.85, danceability=0.72, valence=0.60 (Spotify's audio features)

**Step 2 — Build user profiles**
Aggregate the feature vectors of items the user has interacted with:
- User profile = average of feature vectors of all liked items
- Or a weighted average (more recent interactions weighted higher)

**Step 3 — Score candidate items**
Compute cosine similarity between the user profile vector and each candidate item vector. Recommend top-N highest-similarity items.

**Example — movie preferences:**
- User liked: The Dark Knight [action=1, thriller=1, sci-fi=0] and Inception [action=1, thriller=0, sci-fi=1]
- User profile = average = [action=1.0, thriller=0.5, sci-fi=0.5]
- New movie Tenet [action=1, thriller=0.5, sci-fi=1.0] → high cosine similarity → recommend

**Strengths:**
- Works with just a few user interactions (bootstraps quickly)
- Explainable: "Recommended because you liked action films"
- No cold start for new items — just add the item's feature vector

**Weaknesses:**
- Filter bubble: user gets stuck in a loop of similar content, never discovers new genres
- Feature quality matters — if item descriptions are poor, recommendations are poor
- Misses social signal: "many people like you are also exploring jazz" is invisible to content-based

## Q5: What is matrix factorization? Explain SVD and ALS.

**Intuition:** Instead of storing the full sparse user-item matrix (millions × millions, mostly empty), matrix factorization learns compact representations: each user gets a short "taste vector" and each item gets a short "attribute vector." A user's predicted rating for an item is just the dot product of these two vectors.

**The key equation:**
$$R \approx U \cdot V^T$$
- R = user-item rating matrix (n_users × n_items, very sparse)
- U = user embedding matrix (n_users × k latent factors)
- V = item embedding matrix (n_items × k latent factors)
- k = number of latent factors — typically 50–300

**Predicted rating for user u, item i:**
$$\hat{r}_{ui} = \mathbf{u}_u \cdot \mathbf{v}_i = \sum_{f=1}^{k} u_{uf} \cdot v_{if}$$

**What are latent factors?** The model discovers them automatically. In a movie context, some dimensions roughly correspond to "action vs drama", "recent vs classic", "indie vs blockbuster" — but the model learns these without labels.

**SVD (Singular Value Decomposition):**
Classic matrix factorization: decomposes R = U Σ Vᵀ exactly for dense matrices. Problem: the rating matrix is 99%+ sparse. Simon Funk's modified SVD handles this by only minimizing error over observed ratings (ignoring blanks).

**ALS (Alternating Least Squares) — the production standard:**
- Fix V, solve for each user vector u analytically (closed-form least squares)
- Fix U, solve for each item vector v analytically
- Alternate until convergence

**Why ALS over gradient descent?**
- Each sub-problem has a closed-form solution → no learning rate tuning
- Highly parallelizable — each user's vector can be updated independently
- Handles implicit feedback natively with confidence weighting
- Used at Netflix, Spotify at scale (Spark MLlib's ALS is the default)

**Loss function:**
$$\min_{U, V} \sum_{(u,i) \in \text{observed}} (r_{ui} - \mathbf{u}_u \cdot \mathbf{v}_i)^2 + \lambda(\|\mathbf{u}_u\|^2 + \|\mathbf{v}_i\|^2)$$

The λ term is L2 regularization — prevents users/items with very few interactions from overfitting.

---

**ALS worked example (k=2 latent factors, 3 users × 3 movies):**

Starting rating matrix R (? = unobserved):

|        | Movie A | Movie B | Movie C |
|--------|---------|---------|---------|
| User 1 | 5       | 3       | ?       |
| User 2 | 4       | ?       | 1       |
| User 3 | ?       | 2       | 4       |

**Iteration 1 — Fix V, solve for U:**

Assume V (item embeddings) is randomly initialised:
- Movie A = [1.0, 0.5]
- Movie B = [0.5, 1.0]
- Movie C = [0.2, 0.9]

For User 1 (observed: Movie A=5, Movie B=3), solve the least-squares problem:

$$\mathbf{u}_1 = \arg\min_u \left[(5 - \mathbf{u} \cdot [1.0, 0.5])^2 + (3 - \mathbf{u} \cdot [0.5, 1.0])^2\right] + \lambda\|\mathbf{u}\|^2$$

This is a standard (VᵀV + λI)⁻¹Vᵀr equation — yields say u₁ = [3.8, 1.2].

**Iteration 1 — Fix U (just updated), solve for V:**

Now solve for each movie's vector using the users who rated it. Movie A was rated by User 1 (5) and User 2 (4) → solve least-squares over u₁ and u₂ → yields say vA = [1.1, 0.4].

**After convergence — predict missing entries:**

$$\hat{r}_{1,C} = \mathbf{u}_1 \cdot \mathbf{v}_C = [3.8, 1.2] \cdot [0.2, 0.9] = 0.76 + 1.08 = \mathbf{1.84}$$
$$\hat{r}_{3,A} = \mathbf{u}_3 \cdot \mathbf{v}_A = [0.5, 3.1] \cdot [1.1, 0.4] = 0.55 + 1.24 = \mathbf{1.79}$$

User 3 is predicted to dislike Movie A (1.79/5) → don't recommend it. User 1 is also predicted to dislike Movie C → don't recommend it.

**Key insight:** ALS never sees the ? cells during training — it only minimises error on observed ratings. The latent vectors it learns encode the *reason* behind the ratings (genre preference, tempo, tone) even though those reasons were never given as labels.

---

**Content-Based Filtering vs Item-Item Collaborative Filtering — side by side:**

Both answer the same question — "given an item the user liked, what else should we recommend?" — but they use completely different signals.

| | Item-Item CF | Content-Based |
|---|---|---|
| **Similarity defined by** | Users who rated both items similarly | Item features (genre, tags, audio, text) |
| **Data needed** | Rating/interaction history across many users | Item metadata or raw content |
| **Example signal** | "Inception and Interstellar were both rated 5★ by the same 10k users" | "Both are sci-fi, Christopher Nolan, 2h30m runtime, dark tone" |
| **Cold start (new item)** | Fails — no ratings yet to compare | Works — just use its feature vector |
| **Serendipity** | High — can surface genre-crossing surprises | Low — locked to user's known taste profile |
| **Explainability** | Hard — "others who liked X liked Y" | Easy — "because you like action + sci-fi" |
| **Production use** | Amazon's original CF; YouTube candidates | Spotify audio features; news article recommenders |

**Concrete example — recommending from "User liked Inception":**

*Item-Item CF approach:*
Look at every user who rated Inception highly. Find which other movies those same users rated highly. If 8,000 users gave Inception 5★ and 6,500 of them also gave Interstellar 5★ → cosine similarity between Inception's and Interstellar's user-rating vectors is high → recommend Interstellar.
No knowledge of genre, director, or runtime needed — just the crowd's rating pattern.

*Content-Based approach:*
Inception feature vector: [sci-fi=1, thriller=1, director=Nolan, runtime=148min, year=2010].
User profile = average of all liked item vectors → strong weight on sci-fi, thriller, Nolan.
Score every unseen movie by cosine similarity to this profile → Interstellar scores high because it shares sci-fi, Nolan, similar runtime.
No other users' data needed — works from day one for a brand new user.

**The decisive difference:** Item-Item CF requires a crowd of users to have already rated both items together. Content-based needs only the item's properties and at least one interaction from the target user. This is why content-based bootstraps new users and new items, while item-item CF produces higher-quality and more surprising recommendations once enough data accumulates.

## Q6: What is the cold start problem and how do you solve it?

**Intuition:** A recommender learns from past behavior. What do you recommend to someone brand new with zero history? Or a brand new item that nobody has interacted with yet? That's cold start — the system has no signal to work with.

**Three types of cold start:**
1. **New user cold start** — signed up 5 minutes ago, zero interactions
2. **New item cold start** — just added to the catalog, no ratings or clicks yet
3. **New system cold start** — the entire platform is brand new with no data at all

**Solutions for new USER cold start:**

| Solution | How it works | Used by |
|---|---|---|
| Onboarding survey | Ask about preferences on first login (genres, artists, topics) | Spotify, Netflix |
| Popularity-based fallback | Show the most popular items globally or by demographic | Most platforms |
| Demographic cluster | Assign new user to a user cluster based on age/location/device, recommend that cluster's favorites | Amazon |
| Exploration session | Show diverse items, observe first few clicks, rapidly personalize | TikTok |

**Solutions for new ITEM cold start:**

| Solution | How it works |
|---|---|
| Content embedding | Use item features (text, image, tags) to generate an embedding. Find similar existing items and inherit their placement. |
| Exploration boost | Artificially inject the new item into a small fraction of recommendation slots to gather early signal fast |
| Hybrid model transition | Start with content-based embedding as the item vector; switch to CF embedding once enough interactions accumulate |

**Key insight:** Cold start is why production systems are hybrid. Pure CF fails at cold start, but content-based never needs historical interactions. A real system transitions from content-based to CF as interactions accumulate per item and per user.

## Q7: What is the difference between explicit and implicit feedback?

**Explicit feedback:** The user directly and intentionally expresses a preference.
- Star ratings, thumbs up/down, "Not Interested" button
- High quality signal — no ambiguity about what it means
- Low volume — most users rarely rate (rating fatigue)

**Implicit feedback:** Inferred from behavior, not a direct statement.
- Clicks, purchases, watch time, replays, search queries, scroll depth, add-to-cart
- Very high volume — every user action generates a data point
- Noisy — a click doesn't mean "loved it" (could be curiosity, misclick, or partial interest)

| | Explicit | Implicit |
|---|---|---|
| **Signal quality** | High | Noisy |
| **Volume** | Low | Very high |
| **Negative signal** | Clear (1-star = disliked) | Ambiguous (didn't click ≠ disliked — may not have seen it) |
| **Production reality** | Rare — Netflix even removed star ratings | Dominant — most systems are built on this |

**How to handle implicit feedback in the model:**

Treat it as a **positive-unlabeled (PU)** problem:
- Observed interactions = positive examples (user showed interest)
- Unobserved items ≠ negative examples (user may simply not have seen them)
- Use **confidence weighting**: a purchase gets high confidence; a single scroll-past gets low confidence

In weighted ALS: confidence $c_{ui} = 1 + \alpha \cdot r_{ui}$ where $r_{ui}$ is the raw interaction count and α controls how much each additional interaction increases confidence. The model fits observed interactions harder than the zeros.

## Q8: How do two-tower models work?

**Intuition:** A two-tower model learns separate neural network representations for users and items, then scores candidate items by computing similarity between the user embedding and each item embedding in vector space. It's the backbone of modern large-scale retrieval at Google, YouTube, and TikTok.

**Architecture:**

```
User Features ──► User Tower (MLP layers) ──► User Embedding (e.g., 256-dim)
                                                        │
                                              Dot product / Cosine similarity ──► Score
                                                        │
Item Features ──► Item Tower (MLP layers) ──► Item Embedding (e.g., 256-dim)
```

**User tower inputs:**
- Watched history (average of item embeddings, or sequence model output)
- User demographics, device, location
- Context: time of day, session length, how they arrived

**Item tower inputs:**
- Item ID embedding (learned)
- Content features: text description, genre tags, image embedding
- Popularity, recency, language

**Training objective:**
- Positive pair: (user, item they interacted with) → maximize similarity
- Negative pairs: (user, items they didn't interact with) → minimize similarity
- Loss: in-batch softmax cross-entropy (treating all other items in the batch as negatives)

**The key production insight — pre-computed item embeddings:**
During inference, all item embeddings are pre-computed and indexed offline.
At query time: only the user tower runs a forward pass (fast!), producing a user embedding.
Then an approximate nearest neighbor (ANN) search finds the most similar items in milliseconds.
This separation is what makes two-tower models work at billion-item scale.

**Two-tower = retrieval stage (returns top-K candidates).**
A heavier ranking model then re-scores those K candidates with richer cross-feature interactions. This two-stage funnel is universal at large-scale recommender systems.

## Q9: How does a recommender system work at inference time?

**Intuition:** You can't score all 10 million items in real time — that would take seconds per request. Instead, production systems use a funnel: start broad and fast, get progressively more precise, score a small final set deeply.

**The standard 3-stage inference pipeline:**

```
10,000,000 items
       │
       ▼ Stage 1: Candidate Retrieval  ← fast ANN search, rules, CF lookup
  1,000–10,000 candidates
       │
       ▼ Stage 2: Pre-ranking          ← lightweight model (logistic regression / tiny MLP)
   100–500 candidates
       │
       ▼ Stage 3: Ranking              ← full model, rich cross-features
    10–50 final recommendations
       │
       ▼ Post-processing               ← diversity, dedup, business rules, A/B routing
    Final feed / page
```

**Stage 1 — Candidate Retrieval (latency target: < 50ms)**
- **Two-tower ANN:** Pre-compute all item embeddings. At query time, run the user tower, then query FAISS / ScaNN for the nearest item embeddings.
- **CF lookup:** Pre-computed user-item similarity tables
- **Business rules:** Always include new releases, trending items, items from preferred categories

**Stage 2 — Pre-ranking (optional, latency target: < 20ms)**
A lightweight logistic regression or tiny MLP scores each candidate with basic features.
Eliminates obvious mismatches cheaply. Reduces 10K → 500.

**Stage 3 — Ranking (latency target: < 100ms)**
A full ML model (XGBoost, deep neural net with cross-feature interactions) scores each candidate with rich signals:
- User × item interaction features (has this user interacted with this creator before?)
- Real-time context (current session, trending signals)
- Historical CTR and purchase rate for this item segment
Output: predicted probability of engagement. Sort by score. Return top N.

**Post-processing:**
- Deduplicate: no two items from the same creator back-to-back
- Diversity: ensure not all items are the same category
- Business constraints: inject sponsored items, suppress out-of-stock or policy-violating content
- A/B routing: send 10% of traffic to experimental model

## Q10: How do you evaluate a recommender system?

**Intuition:** Unlike binary classification where one prediction is right or wrong, a recommender outputs a ranked list. Evaluation must reward putting the right items near the top of the list — not just anywhere in it.

**Offline setup for all metrics:** For each user, hold out their next K real interactions as ground truth. The model generates a ranked list of N recommendations. Compare the two.

---

**Precision@K** — Of the top K recommendations, what fraction did the user actually engage with?

$$\text{Precision@K} = \frac{\text{Relevant items in top K}}{K}$$

Example: K=5, user clicked 2 of the 5 recommended → Precision@5 = 0.40

---

**Recall@K** — Of all items the user actually engaged with, what fraction appeared in the top K?

$$\text{Recall@K} = \frac{\text{Relevant items in top K}}{\text{Total relevant items for user}}$$

Example: User had 10 real interactions; 3 appeared in the top-10 recommendations → Recall@10 = 0.30

---

**Hit Rate@K (HR@K)** — Did at least ONE relevant item appear in the top K? Binary per user, averaged across all users.

$$\text{HR@K} = \frac{\text{Users with ≥1 relevant item in top K}}{\text{Total users}}$$

Simple and intuitive: "What fraction of users received at least one good recommendation?"

---

**MRR (Mean Reciprocal Rank)** — How high up the list was the FIRST relevant item?

$$\text{MRR} = \frac{1}{|U|} \sum_{u} \frac{1}{\text{rank of first relevant item for user } u}$$

First relevant item at rank 1 → score 1.0; rank 2 → 0.5; rank 5 → 0.2. Averaged over all users.

**Worked example — MRR across 3 users (K=5):**

| User | Recommended list (rank 1→5) | First relevant item at rank | Reciprocal rank |
|------|-----------------------------|-----------------------------|-----------------|
| U1   | [A, B, C, D, E] — relevant: {C, E} | rank 3 (C) | 1/3 = 0.333 |
| U2   | [A, B, C, D, E] — relevant: {A}    | rank 1 (A) | 1/1 = 1.000 |
| U3   | [A, B, C, D, E] — relevant: {D}    | rank 4 (D) | 1/4 = 0.250 |

MRR = (0.333 + 1.000 + 0.250) / 3 = **0.528**

```python
def mrr(recommended_lists, relevant_sets):
    # recommended_lists: list of ranked item lists, one per user
    # relevant_sets: list of sets of ground-truth items, one per user
    rr_scores = []
    for rec, rel in zip(recommended_lists, relevant_sets):
        rr = 0.0
        for rank, item in enumerate(rec, start=1):   # rank starts at 1
            if item in rel:
                rr = 1.0 / rank                       # reciprocal of first hit rank
                break
        rr_scores.append(rr)                          # 0 if no relevant item found
    return sum(rr_scores) / len(rr_scores)            # average across users

recommended = [["A","B","C","D","E"], ["A","B","C","D","E"], ["A","B","C","D","E"]]
relevant    = [{"C","E"},             {"A"},                  {"D"}]
print(f"MRR = {mrr(recommended, relevant):.3f}")      # MRR = 0.528
```

---

**NDCG@K (Normalized Discounted Cumulative Gain)** — the gold standard for ranking quality. Rewards putting relevant items higher in the list via a logarithmic discount.

**Step 1 — DCG@K:**
$$\text{DCG@K} = \sum_{i=1}^{K} \frac{\text{rel}_i}{\log_2(i+1)}$$

rel_i = 1 if position i is relevant, 0 otherwise. Discount: rank 1 = 1.0, rank 2 = 0.63, rank 3 = 0.5.

**Step 2 — IDCG@K:** DCG if the list were in perfect order.

**Step 3:** NDCG@K = DCG@K / IDCG@K (0 to 1).

**Worked example — NDCG@5 for one user, ground truth relevant = {B, D}:**

Model ranking: [A, B, C, D, E]

| Rank i | Item | rel_i | log₂(i+1) | rel_i / log₂(i+1) |
|--------|------|-------|-----------|-------------------|
| 1      | A    | 0     | 1.000     | 0.000             |
| 2      | B    | 1     | 1.585     | 0.631             |
| 3      | C    | 0     | 2.000     | 0.000             |
| 4      | D    | 1     | 2.322     | 0.431             |
| 5      | E    | 0     | 2.585     | 0.000             |

- DCG@5 = 0 + 0.631 + 0 + 0.431 + 0 = **1.062**
- Ideal order [B, D, A, C, E]: IDCG@5 = 1/log₂(2) + 1/log₂(3) = 1.000 + 0.631 = **1.631**
- NDCG@5 = 1.062 / 1.631 = **0.651**

```python
import math

def dcg_at_k(recommended, relevant, k):
    dcg = 0.0
    for rank, item in enumerate(recommended[:k], start=1):   # consider top-k only
        if item in relevant:
            dcg += 1.0 / math.log2(rank + 1)                 # logarithmic position discount
    return dcg

def ndcg_at_k(recommended, relevant, k):
    actual_dcg = dcg_at_k(recommended, relevant, k)          # DCG of the model's ranking
    ideal_hits = min(len(relevant), k)                       # max possible hits in top-k
    ideal_ranking = list(relevant)[:ideal_hits]              # best possible ordering
    ideal_dcg = dcg_at_k(ideal_ranking, relevant, k)         # IDCG
    return actual_dcg / ideal_dcg if ideal_dcg > 0 else 0.0  # normalise; guard div-by-zero

rec = ["A", "B", "C", "D", "E"]
rel = {"B", "D"}
print(f"DCG@5  = {dcg_at_k(rec, rel, 5):.3f}")   # DCG@5  = 1.062
print(f"NDCG@5 = {ndcg_at_k(rec, rel, 5):.3f}")  # NDCG@5 = 0.651
```

**Key intuition:** NDCG penalises finding B at rank 2 instead of rank 1, and D at rank 4 instead of rank 2 — the logarithmic discount makes every position upgrade matter less as you go deeper, matching how users rarely scroll far down a list.

**Beyond accuracy — catalog-level metrics:**

| Metric | What it measures | Why it matters |
|---|---|---|
| **Coverage** | % of the item catalog that ever appears in recommendations | Low coverage = popularity bias |
| **Diversity** | Average pairwise dissimilarity among the recommended items | Prevents repetitive feeds |
| **Novelty** | Are recommendations items the user hasn't seen before? | Drives discovery |
| **Serendipity** | Surprising yet relevant recommendations | Prevents filter bubbles |

**Offline vs Online evaluation:**

Offline metrics (NDCG, Precision@K) measure on historical held-out data — fast and cheap. Good for rapid iteration.

Online metrics (CTR, watch time, purchases) measured via A/B tests — definitive but expensive and slow.

**Critical rule:** Offline NDCG improvement does NOT always translate to online CTR improvement. A model can score perfectly on past data but fail on live traffic due to distribution shift or feedback loops. Always validate with an A/B test before shipping.

## Q11: What is the explore-exploit trade-off in recommendations?

**Intuition:** A recommender that only shows items it's confident you like (exploitation) will narrow your feed into a filter bubble and never discover your new interests. But showing only unfamiliar items (exploration) gives a bad user experience. The ideal system does both.

**Exploitation:** Recommend items the model is confident the user will enjoy, based on proven history.

**Exploration:** Occasionally recommend items with uncertain appeal — to gather new signal and potentially discover new preferences.

**Why exploration matters:**
- The model only learns about items it has recommended — never recommending new items means never learning about them
- A newly released item has no data; pure exploitation never surfaces it
- User tastes evolve — a jazz fan might not listen to jazz in the morning; pure exploitation misses this

**Common approaches:**

**ε-greedy:** With probability ε show a random item; with probability 1−ε show the best predicted item. Simple, robust baseline.

**Upper Confidence Bound (UCB):** Score each item by (predicted score + exploration bonus proportional to uncertainty). Items rarely shown get a large bonus → natural exploration.

**Thompson Sampling:** Maintain a probability distribution over each item's expected reward. Sample from distributions and recommend highest sampled value. Uncertain items occasionally get sampled high → organic exploration.

**Production reality:** Most large platforms reserve 10–20% of feed slots explicitly for exploration — new releases, trending items in adjacent categories, items from under-represented creators.

## Q12: What is popularity bias and how do you handle it?

**Intuition:** Recommenders have a rich-get-richer problem. Popular items get many clicks → model sees more training data for them → model recommends them more → they get even more clicks. Niche items with passionate audiences never break through because they lack initial exposure.

**Why it happens:**
- Training data follows a power-law — the top 1% of items account for 50%+ of interactions
- The model over-indexes on popularity as an implicit feature
- Cold-start items never accumulate enough signal to rank highly

**How to detect it:**
- **Gini coefficient** of recommendation distribution: high Gini = concentrated on few items
- **Catalog coverage**: if only 5% of items ever appear in recommendations, popularity bias is severe
- Compare average popularity of recommended items vs. average popularity of all items

**Solutions:**

**1. Inverse popularity weighting during training:**
Down-weight popular items so the model doesn't over-optimize for them:
$$w_{ui} = \frac{1}{\text{pop}(i)^\alpha}, \quad \alpha \in [0, 0.5]$$

**2. Popularity-aware ranking:**
Subtract a popularity penalty from scores at ranking time. Penalize items that already appear in the top-N for more than X% of users.

**3. Coverage constraints:**
Hard rule: ensure at least Y% of recommended items come from the "long tail" (items with fewer than Z total interactions).

**4. Re-ranking for diversity:**
Post-processing step: re-rank the top-50 to ensure variety by category, popularity tier, and recency before returning the final top-10.

**5. Counterfactual debiasing:**
Model the probability that an item was shown (propensity) and down-weight interactions that happened only because the item was already popular. Inverse Propensity Scoring (IPS) corrects for exposure bias in the training signal.

**Trade-off:** De-biasing reduces short-term CTR (popular items are popular for a reason) but improves long-term user retention, catalog health, and creator ecosystem fairness. Frame it as a long-term value vs. short-term engagement decision.

## Q13: What is MAB2Rec and how do multi-armed bandits power a recommender system?

**Intuition:** Think of a slot machine (a "bandit") with many arms — one for each item in your catalog. Each time you pull an arm for a user, you get a reward (click = 1, no-click = 0). A multi-armed bandit (MAB) algorithm learns *which arm to pull for which user* by balancing two goals: exploit what already works well, and explore uncertain arms that might be even better. MAB2Rec is a Python library (from Fidelity AI Center of Excellence, presented at AAAI 2024) that wraps this framework into a full recommendation pipeline.

**The core mapping:**

| Bandit concept | Recommender concept |
|---|---|
| Arms | Items in the catalog |
| Context | User features at the time of recommendation |
| Reward | Click = 1, no-click = 0 (or watch time, purchase, etc.) |
| Policy | The algorithm that decides which item to recommend given the user context |

---

### The 3-step recommendation cycle

Every request goes through this loop — and crucially, the model updates *inside* the loop, not in an overnight batch job:

```
[User Context Vector (X)]
        │
        ▼
[Bandit Policy]  ──────────────────────► Top-K Items recommended
        ▲                                        │
        │                           User clicks / ignores
        │                                        │
        └──── .fit(reward) ◄─── Reward = 1 (click) or 0 (ignore)
              (online update)
```

**Step 1 — Context aggregation:** When a user visits the platform, Mab2Rec compiles a context vector $X$ combining user attributes (age, historical flags), environmental signals (device type, time of day), and item features.

**Step 2 — Policy evaluation (Explore vs Exploit):** The context vector is passed through the active bandit policy.
- *Exploit* — recommend the item with highest predicted reward given the context.
- *Explore* — occasionally recommend a less-certain item to avoid locking users into a rigid bubble and to gather signal on new/unpopular items.

**Step 3 — Feedback and reward routing:** The user either clicks (reward=1) or ignores (reward=0). This binary signal is immediately routed back via a lightweight `.fit()` call, updating the model's weights in real time — no overnight retraining pipeline needed.

---

### Why bandits instead of a traditional ML model?

A two-tower or matrix factorization model treats recommendations as a static supervised learning problem — it learns from historical data and then deploys a fixed function. A bandit policy is **online and adaptive**: it updates its beliefs with each new interaction, continuously adjusting recommendations. This makes it naturally suited for:
- Cold start — new items get exploration probability immediately
- Changing user preferences — the policy adapts without retraining
- Explicit exploration-exploitation management

---

### Bandit algorithms in MAB2Rec (via MABWiser)

**Context-free bandits** — don't use user features, only item-level statistics:

| Algorithm | How it works | When to use |
|---|---|---|
| **Popularity** | Always recommend the most clicked items globally | Baseline; good cold-start fallback |
| **Random** | Random item from eligible pool | Exploration baseline, fairness testing |
| **ε-Greedy** | With probability ε pick randomly; with probability 1−ε pick highest-reward arm | Simple, interpretable, robust |
| **UCB1** | Score = mean reward + confidence bonus (wider for rarely-shown items) | When you want theoretically sound exploration |
| **Thompson Sampling** | Maintain a Beta(α, β) belief per item; sample from each; recommend highest sample | Probabilistic; very effective in practice |
| **Softmax** | Sample items proportional to exp(reward/τ); τ controls exploration temperature | Smooth exploration, tunable |

**Contextual bandits** — incorporate user feature vectors into the decision:

| Algorithm | How it works |
|---|---|
| **LinGreedy** | Fit a linear model (reward ~ context features) per item; ε-greedy exploration on top |
| **LinUCB** | Fit a linear model; score = linear prediction + UCB bonus (exploration reward) |
| **LinTS (Linear Thompson Sampling)** | Bayesian linear regression per item; sample from posterior; recommend highest sample |

**LinUCB score formula:**
$$\text{score}_{ia} = \hat{\theta}_a^\top x_i + \alpha \sqrt{x_i^\top A_a^{-1} x_i}$$

where $x_i$ = user context features, $\hat{\theta}_a$ = learned weight vector for item $a$, $A_a$ = feature covariance matrix for item $a$, $\alpha$ = exploration parameter. The second term is wider (more exploration) when item $a$ has been shown rarely or to contexts dissimilar to $x_i$.

**LinUCB — Optimism in the Face of Uncertainty (intuition):**

```
Item A (Popular — 10,000 clicks):
  Point estimate:       12%
  Confidence interval:  [11% ──────── 13%]
  Upper bound (UCB):    13%

Item B (New — shown twice):
  Point estimate:        5%
  Confidence interval:  [1% ────────────────────── 20%]
  Upper bound (UCB):    20%

LinUCB recommends: Item B  (20% UCB > 13% UCB)
```

Even though Item A has a higher baseline prediction (12% vs 5%), LinUCB picks Item B because its **upper confidence bound** is higher. If the user ignores Item B, its baseline drops and the confidence interval shrinks. If they click, the baseline rises. Each impression collapses the uncertainty — this is "Optimism in the Face of Uncertainty."

**LinTS — Bayesian exploration via posterior sampling:**

All three contextual policies (LinGreedy, LinUCB, LinTS) use Ridge Regression internally to predict reward from context features. LinTS adds a Bayesian layer: instead of storing a fixed weight for each feature, it stores a **probability distribution** (Gaussian) over each weight.

```
Well-known item (small variance):        New item (large variance):
         /\                                         
        /  \                              /──────────────────\
_______/    \_______                _____/                    \_____
   (samples ≈ 12% every time)       (could sample 2% or 25% by chance)
```

Every time a recommendation is requested, LinTS **samples** from each weight distribution and computes a score. Items with uncertain (wide) distributions occasionally get a very high sampled score by chance — forcing organic exploration without any explicit epsilon or alpha cutoff. The exploration is automatically proportional to the mathematical probability that an item might be optimal.

| Policy | Exploration mechanism | Key hyperparameter |
|---|---|---|
| **LinGreedy** | ε% of requests pick a random item | `epsilon` (0.0 = full exploit, 1.0 = full explore) |
| **LinUCB** | Score = prediction + uncertainty bonus | `alpha` (higher = more exploration) |
| **LinTS** | Sample from weight distributions; uncertain items get lucky high scores | None — exploration is automatic |

---

### Step-by-step numerical walkthrough — how each policy scores an item

**Setup:** User Alex (age=25, male → context vector $X = [25, 1]$) visits an e-commerce app. The model for Item A (leather jacket) has trained weights $\beta = [0.01, 0.15]$ and intercept $0.05$.

**Base linear regression score (shared by all three policies):**

$$\text{Base Score} = (25 \times 0.01) + (1 \times 0.15) + 0.05 = 0.25 + 0.15 + 0.05 = \mathbf{0.45}$$

Interpretation: 45% estimated probability Alex clicks the jacket. Each policy now handles this 0.45 differently.

---

**Policy 1 — LinGreedy:** use the score directly, but flip a coin first.

```
epsilon = 0.10  (10% explore)

Random draw = 0.73  → 73% > 10%  →  EXPLOIT
Final ranking score = 0.45  (raw prediction, used as-is)

If random draw had been 0.04  → 4% < 10%  →  EXPLORE
Final action = randomly pick any item from catalog (0.45 discarded)
```

**Policy 2 — LinUCB:** inflate the score by an uncertainty bonus.

Item A is new — high standard error. The uncertainty term $\sigma = 0.30$, $\alpha = 1.0$:

$$\text{LinUCB Score} = \underbrace{0.45}_{\text{base}} + \underbrace{1.0 \times 0.30}_{\alpha \cdot \sigma} = \mathbf{0.75}$$

```
Established Item B:  base = 0.52,  σ = 0.03  →  LinUCB score = 0.52 + 0.03 = 0.55
New      Item A:     base = 0.45,  σ = 0.30  →  LinUCB score = 0.45 + 0.30 = 0.75  ← wins

Item A is recommended even though its base prediction is lower.
Once shown and clicked/ignored, σ shrinks → the bonus collapses.
```

**Policy 3 — LinTS:** jitter the weights before computing the score.

The model stores distributions, not point estimates. Each weight has a mean and a standard deviation:

| Weight | Mean | Std dev | Sampled value (this request) |
|---|---|---|---|
| $\beta_1$ (age) | 0.010 | 0.005 | **0.012** |
| $\beta_2$ (gender) | 0.150 | 0.020 | **0.140** |

$$\text{LinTS Score} = (25 \times 0.012) + (1 \times 0.140) + 0.05 = 0.30 + 0.14 + 0.05 = \mathbf{0.49}$$

On the next page load, fresh samples are drawn — the score might be 0.41 or 0.58. For a new item with wide distributions, a tail sample could push the score to 0.80+, forcing exploration with no explicit threshold.

**Final ranking scores used for this single request:**

| Policy | Score used for ranking | How it was derived |
|---|---|---|
| LinGreedy | **0.45** (or random item) | Raw regression prediction |
| LinUCB | **0.75** | Prediction + uncertainty bonus |
| LinTS | **0.49** | Regression with randomly sampled weights |

## Q14: How is training data structured for a bandit-based recommender? (user features, item features, clicks, impressions)

**Intuition:** A bandit recommender learns from a table of "who was shown what, and did they click?" Each row is one (user, item, outcome) tuple enriched with the user's context at the time. The learning signal comes from the ratio of clicks to impressions.

### Core interaction table

```
user_id  | item_id | response | timestamp
---------|---------|----------|----------
u_001    | item_42 |    1     | 2024-01-10
u_001    | item_07 |    0     | 2024-01-10
u_002    | item_15 |    0     | 2024-01-11
u_002    | item_42 |    1     | 2024-01-11
```

- **user_id**: unique user identifier
- **item_id**: which item was shown (the "arm" that was pulled)
- **response**: 1 = click/positive engagement, 0 = impression with no engagement
- **timestamp**: for temporal train/test split

**Critical distinction from supervised ML:**
In a standard ML dataset you choose which rows to include. In a bandit dataset, the rows are *logged decisions* — items were shown to users according to the old recommendation policy, not randomly. This creates **logging bias**: items that were never shown have no data, so the model cannot learn their true reward. This is the **offline bandit evaluation problem**.

---

### User features table

```
user_id  | age_bucket | tenure_days | avg_session_len | pref_category_1 | pref_category_2 | ...
---------|------------|-------------|-----------------|-----------------|-----------------|-----
u_001    |    25-34   |     180     |      12.3       |    technology   |    finance      | ...
u_002    |    45-54   |      30     |       6.1       |    health       |    lifestyle    | ...
```

These are the **context features** fed to the contextual bandit at both training and inference time. The bandit uses these to estimate "for a user with *these* features, which item has the highest expected click probability?"

**What goes into user features:**
- Demographic signals (age bucket, location, device type)
- Behavioral signals (session length, days since last visit, engagement rate)
- Historical preference signals (top categories interacted with, recency-weighted genre vector)
- Account signals (tenure, plan type, onboarding completion)

---

### Item features (optional in MAB2Rec)

In MAB2Rec, items are modeled as **arms** (labels). The policy learns a reward estimate per arm directly. Item content features can be incorporated via:
- **TextWiser integration**: embed item text descriptions → use as additional arms metadata
- **Pre-built item embeddings**: reduce item embeddings to categorical cluster IDs → treat clusters as arms
- **Hybrid**: user features as context → bandit policy → item-level reward estimator

---

### Clicks vs. impressions — what the bandit learns

The bandit observes two signals per (user, item) pair:

| Signal | Meaning | How used |
|---|---|---|
| **Impression** | Item was shown to user | Denominator — we know the bandit had a chance to get a reward |
| **Click** | User clicked (or purchased, or watched > threshold) | Numerator — the reward was positive |
| **CTR per arm** | clicks / impressions for each item | Prior for context-free bandits (Popularity, UCB) |

For contextual bandits (LinUCB, LinTS), the model goes further: it fits a function `f(user_features) → expected click probability` for each item, allowing personalized scoring rather than a single CTR estimate.

---

### Train/test split for bandit data

Always split temporally — the same as any production ML system:

```
Training data: all (user, item, response) rows before date T
Test data:     rows in [T, T + evaluation_window]
```

**Cross-validation for bandits:** MAB2Rec uses temporal K-fold CV — fold 1 trains on month 1 and tests on month 2; fold 2 trains on months 1–2 and tests on month 3. This simulates the actual deployment scenario.

## Q15: How does inference work in a bandit-based recommender system?

**Intuition:** At inference time the bandit doesn't search a vector space — it asks "given *this user's context right now*, which item do I predict has the highest reward (click probability)?". The model evaluates every eligible item for the user and returns the top-K by predicted score.

### Inference pipeline

```
User arrives → fetch user features → score all eligible items → return top-K

User features (context vector x_i)
        │
        ▼
For each eligible item a:
  context-free bandit:   score = UCB or Thompson sample from Beta(clicks_a, impressions_a - clicks_a)
  contextual bandit:     score = θ̂_a · x_i + exploration_bonus(x_i, A_a)
        │
        ▼
Sort items by score → return top_k
```

---

### How each algorithm scores at inference

**Popularity** (context-free):
$$\text{score}_a = \frac{\text{clicks}_a}{\text{impressions}_a}$$
Recommend the items with the highest historical CTR — no user context.

**ε-Greedy** (context-free):
- With probability ε: pick a random item (explore)
- With probability 1−ε: pick item with highest historical CTR (exploit)

**UCB1** (context-free):
$$\text{score}_a = \hat{\mu}_a + \sqrt{\frac{2 \ln N}{n_a}}$$
- $\hat{\mu}_a$ = empirical CTR for item $a$
- $N$ = total impressions served so far
- $n_a$ = impressions for item $a$ specifically
- Items shown fewer times get a larger bonus → automatic exploration

**Thompson Sampling** (context-free):
```python
for each item a:
    alpha = clicks[a] + 1        # successes (Beta prior α=1)
    beta  = (impressions[a] - clicks[a]) + 1  # failures (Beta prior β=1)
    score[a] = np.random.beta(alpha, beta)     # sample from posterior
# Recommend item with highest sampled score
```

Items with uncertainty (few impressions) have a wide Beta distribution → sometimes sampled high → organic exploration.

**LinGreedy / LinUCB** (contextual):
```python
# At inference time for user with features x_i
for each item a:
    theta_a = trained_linear_weights[a]        # learned from training data
    A_a_inv = inverse_covariance_matrix[a]     # from training
    predicted_reward = theta_a @ x_i           # linear prediction
    exploration_bonus = alpha * sqrt(x_i @ A_a_inv @ x_i)  # UCB term
    score[a] = predicted_reward + exploration_bonus  # LinUCB
# Return top_k items by score
```

The **exploration bonus** is large when:
- Item $a$ was rarely shown in training (wide covariance matrix $A_a$)
- User's features $x_i$ are unusual / far from training distribution

This makes the system automatically explore more for new items and new user types.

## Q16: What are the negative sampling strategies for recommender systems and when do you use each?

**Intuition:** In a recommender dataset, you have positive examples (user interacted with item) and a vast sea of zeros (user didn't interact). But most zeros are *unlabeled* — the user may not have seen the item, may have seen it but not had the chance to act, or genuinely disliked it. Training the model on all zeros as hard negatives would overwhelm the signal and teach it nothing useful. Negative sampling selects a controlled, representative set of "likely true negatives" to pair with each positive.

**Why this matters:** a dataset with 1M users × 100K items has 10^11 possible (user, item) pairs. Of these, maybe 5M are observed positives — that's a 0.005% positive rate. If you train on all unobserved pairs as negatives, the model just learns to predict "no interaction" for everything.

---

### Strategy 1 — Random uniform sampling (baseline)

**How it works:** For each positive (user, item), randomly sample K items the user has *not* interacted with from the full catalog. These become negatives.

```python
import numpy as np

def random_negatives(user_id, positive_items, all_items, k=4):
    candidates = [i for i in all_items if i not in positive_items]
    return np.random.choice(candidates, size=k, replace=False)
```

**Intuition:** Imagine User A loves sci-fi films. She has watched 50 sci-fi movies. You randomly sample 200 negatives: most will be random genres — romcoms, cooking shows, foreign language films. These are *trivially easy* negatives — the model learns "don't recommend romcoms to sci-fi fans" which it could figure out without this data. **Easy negatives → underpowered model.**

**When to use:** Fast baseline; works when item catalog is small and diverse; first iteration before investing in smarter strategies.

**Ratio:** 1 positive to 4–10 negatives is standard. Too many negatives (1:100) makes training unstable.

---

### Strategy 2 — Popularity-weighted sampling

**How it works:** Sample negatives with probability proportional to item popularity (interaction count). Popular items are sampled more often as negatives.

```python
item_pop = df.groupby('item_id')['response'].count()  # interaction count per item
pop_weights = item_pop ** 0.75  # sublinear — prevents top items from dominating
pop_weights /= pop_weights.sum()

def popularity_weighted_negatives(user_id, positive_items, k=4):
    candidates = pop_weights.drop(index=positive_items, errors='ignore')
    candidates /= candidates.sum()
    return np.random.choice(candidates.index, size=k, p=candidates.values)
```

**Intuition:** Popular items are popular because many users clicked them. A user who *didn't* click a popular item is a stronger signal than a user who didn't click an obscure item — they saw it (likely), knew about it, and passed. These negatives are harder for the model to distinguish from positives, which forces it to learn fine-grained user preferences.

**The 0.75 exponent** (from word2vec's negative sampling) prevents the most popular items from dominating the negative pool while still preferring them over rare items.

**When to use:** Standard choice for matrix factorization and two-tower models; better than uniform for platforms with power-law popularity distributions (most platforms).

---

### Strategy 3 — Exposure-based negatives (hard negatives from impressions)

**How it works:** Use items that were *shown* to the user (impression = 1) but not clicked (response = 0). These are the strongest possible negatives — the user definitively had the opportunity to click and chose not to.

```python
# In your interaction log: response=0 means shown but not clicked
hard_negatives = df[(df['user_id'] == user_id) & (df['response'] == 0)]['item_id']
```

**Intuition:** In your seminar attendance prediction example — if a user received an invitation for seminar X (impression) and didn't register (response=0), that is a true negative. You *know* they were exposed and chose not to attend. This is much cleaner than "never saw it" negatives.

**In a content platform:** User scrolled past a video (impression logged) without clicking → true negative. User just never loaded the page and the video wasn't in the viewport → ambiguous, not a safe negative.

**When to use:** When you have impression logging. This is the gold standard negative signal. Requires a tracking system that logs item exposures, not just clicks.

**Limitation:** Can only generate negatives for items that were actually shown — biases training toward the existing recommendation distribution. Combine with some random negatives to avoid this.

---

### Strategy 4 — In-batch negatives (for two-tower training)

**How it works:** During training, treat every item in the current batch (that isn't a user's true positive) as a negative for that user.

```
Batch: [(u1, i3), (u2, i7), (u3, i2), (u4, i9)]  ← 4 positive pairs

For user u1 (positive item i3):
  negatives = {i7, i2, i9}  ← other items in the batch
```

**Intuition:** You don't need to explicitly sample negatives — the batch *is* the negative pool. This is highly efficient and is the standard in large-scale two-tower training (YouTube, Google).

**Why it works:** In a large batch of random users, the other users' positives are unlikely to be relevant to the current user — they're effectively random negatives. And because they're *real interactions*, they're not trivially easy items (they're things someone clicked on, so the model must learn to distinguish).

**Limitation:** "False negatives" — item $i7$ in the batch might actually be good for user $u1$ but is used as a negative. At large scale this is rare; at small scale it can hurt. Mitigated by in-batch negative mining with deduplication.

**When to use:** Two-tower training at scale; GPU/TPU training where large batches are available.

---

### Strategy 5 — Hard negatives via embedding similarity

**How it works:** After a round of training, embed all items. For each user, find items that are *close to the user's embedding but not interacted with* — these are "near misses" that the model is currently confusing with true positives.

```python
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

def hard_negatives_from_embeddings(user_emb, item_embs, item_ids,
                                   positive_ids, top_k=50):
    sims = cosine_similarity([user_emb], item_embs)[0]    # score all items
    ranked = np.argsort(-sims)                             # sort descending
    # Return top-k similar items that are NOT positives
    return [item_ids[i] for i in ranked
            if item_ids[i] not in positive_ids][:top_k]
```

**Intuition:** If the model already learned that User A likes action films and Item X is an action film she hasn't clicked, Item X is a *hard negative* — it looks like something she should click, but she hasn't. Training on these hard negatives forces the model to learn subtle discriminating features (maybe the director, the release year, or the runtime matters).

**When to use:** After initial training to boost model quality; iterative hard-negative mining; common in production two-tower systems (Google, Spotify). Not for first training iteration (need a reasonable model first to generate meaningful embeddings).

---

### Strategy 6 — Temporal / out-of-window negatives

**How it works:** Take a user's interactions from a *different time window* as negatives for the current prediction window.

**Intuition:** In the seminar example — if User A attended seminars in Q3, their Q1 non-attendances can serve as negatives, representing topics or times they genuinely didn't want to engage with. Their absence in Q1 isn't random — they had access to the system but didn't register.

**When to use:** When you have no exposure signal (like the seminar case — no invitation log) but you have longitudinal user history. Common in e-commerce and subscription platforms.

---

### Decision guide — which strategy for your system

| Situation | Strategy | Ratio |
|---|---|---|
| No exposure/impression log | Random uniform (+ popularity-weighted) | 1:4–10 |
| Have impression log | Exposure-based (shown, not clicked) | 1:2–5 |
| Two-tower / embedding model | In-batch negatives | N/A (batch-based) |
| Model already trained, want to improve | Hard negatives from embeddings | 1:2–4 |
| No click signal, longitudinal history | Temporal out-of-window negatives | 1:3–5 |
| Power-law popularity distribution | Popularity-weighted (pop^0.75) | 1:4–10 |

**Combining strategies (production best practice):**
Most production systems mix strategies — e.g., 50% exposure-based negatives + 30% popularity-weighted random + 20% hard negatives. This gives a diverse negative set: some definitive negatives (exposures), some challenging negatives (popular items the user skipped), and some near-miss negatives (hard) to push the decision boundary.

## Q17: What recommender metrics does Jurity provide and how do you compute them?

**Intuition:** Evaluating a recommender is harder than binary classification — you need to know not just *whether* the right item was predicted, but *where in the ranked list* it appeared, how often users clicked on the recommendations, and whether the recommendations were diverse enough. Jurity (from Fidelity AI Center) provides a unified interface for all standard recommender metrics.

---

### Binary recommender metrics (CTR, AUC)

**CTR — Click-Through Rate**

$$\text{CTR} = \frac{\sum \text{clicks}}{\sum \text{impressions}}$$

Measures what fraction of shown recommendations were clicked. This is the primary online business metric.

```python
from jurity.recommenders import BinaryRecoMetrics
import pandas as pd

actual    = pd.DataFrame({'user_id': [1, 2, 3], 'item_id': [10, 20, 30], 'clicks': [1, 0, 1]})
predicted = pd.DataFrame({'user_id': [1, 2, 3], 'item_id': [10, 20, 30], 'score': [0.9, 0.4, 0.7]})

ctr = BinaryRecoMetrics.CTR(click_column='clicks')
print(ctr.get_score(actual, predicted))  # fraction of clicks among all shown items
```

**Limitation:** CTR can be gamed — showing only the most popular items maximizes CTR in the short run but produces a worse recommender for users.

**AUC** — Area Under the ROC Curve

Standard ranking metric: probability that the model ranks a randomly chosen positive item higher than a randomly chosen negative. AUC = 0.5 is random; AUC = 1.0 is perfect.

**IPS — Inverse Propensity Scoring** (unbiased CTR)

Raw CTR is biased by the recommendation policy — popular items are shown more so they accumulate more clicks. IPS corrects for this:

$$\text{IPS-CTR} = \frac{1}{n} \sum_{i} \frac{r_i}{p_i}$$

where $r_i$ = click/no-click for interaction $i$, $p_i$ = propensity (probability that item $i$ was shown under the logging policy). Items shown with low probability but clicked get higher weight — corrects for exposure bias.

**DR — Doubly Robust Estimation**

Combines IPS with a direct outcome model for lower variance:

$$\text{DR} = \frac{1}{n} \sum_i \left[\hat{r}_i + \frac{r_i - \hat{r}_i}{p_i}\right]$$

where $\hat{r}_i$ is a predicted reward from a model. If the model is accurate, variance is low; if the propensity is accurate, bias is low — "doubly robust" because only one needs to be correct for the estimate to be valid.

---

### Ranking metrics (Precision@K, Recall@K, MAP@K, NDCG)

These metrics evaluate the quality of a top-K recommendation list.

**Precision@K:**
$$\text{Precision@K} = \frac{\text{Relevant items in top K}}{K}$$

"Of the K items I showed you, how many did you actually engage with?"

**Recall@K:**
$$\text{Recall@K} = \frac{\text{Relevant items in top K}}{\text{Total relevant items for user}}$$

"Of all the items you actually care about, how many did I put in my top K?"

**MAP@K — Mean Average Precision:**

For each user, Average Precision (AP) rewards finding relevant items *early* in the list:

$$\text{AP@K} = \frac{1}{\min(R, K)} \sum_{k=1}^{K} \text{Precision@k} \cdot \text{rel}(k)$$

where $R$ = total relevant items, $\text{rel}(k) = 1$ if item at rank $k$ is relevant.

MAP@K = average of AP@K over all users.

**Example:** K=4, relevant = {A, C}
Model ranking: [A, B, C, D] → A at rank 1 (hit), B at rank 2 (miss), C at rank 3 (hit), D (miss)

- Precision@1 = 1/1 = 1.0 (A hit)
- Precision@3 = 2/3 = 0.67 (A and C hit)
- AP@4 = (1.0 + 0.67) / 2 = **0.835**

**NDCG@K:** (see full explanation in Q10 — the gold standard ranking metric, rewards hits earlier in the list)

```python
from jurity.recommenders import RankingRecoMetrics

actual    = pd.DataFrame({'user_id': [1, 2], 'item_id': [10, 20], 'clicks': [1, 1]})
predicted = pd.DataFrame({'user_id': [1, 1, 2, 2],
                          'item_id': [10, 30, 20, 40],
                          'score':   [0.9, 0.7, 0.8, 0.6]})

precision_k = RankingRecoMetrics.Precision(click_column='clicks', k=2)
recall_k    = RankingRecoMetrics.Recall(click_column='clicks', k=2)
map_k       = RankingRecoMetrics.MAP(click_column='clicks', k=2)
ndcg        = RankingRecoMetrics.NDCG(click_column='clicks', k=2)

print(precision_k.get_score(actual, predicted))
print(recall_k.get_score(actual, predicted))
print(map_k.get_score(actual, predicted))
print(ndcg.get_score(actual, predicted))
```

### Diversity metrics (Inter-List and Intra-List Diversity)

**Intra-List Diversity@K** — are the items *within one user's* recommendation list diverse?

$$\text{ILD}(L_u) = \frac{2}{K(K-1)} \sum_{i \in L_u} \sum_{j \in L_u, j \neq i} d(i, j)$$

where $d(i, j)$ = dissimilarity between items $i$ and $j$ (e.g., 1 − cosine_similarity(item_emb_i, item_emb_j)).

High ILD = the 10 recommendations span diverse categories. Low ILD = all 10 recommendations are action films.

**Intuition:** If you recommend 10 sci-fi films to a user who likes sci-fi, Precision@10 might be high, but ILD is low — the user sees zero variety and gets bored. Good recommendations balance relevance (high precision) with variety (high ILD).

**Inter-List Diversity@K** — are recommendation lists *across different users* diverse?

$$\text{InterLD} = 1 - \frac{2}{|U|(|U|-1)} \sum_{u \in U} \sum_{v \in U, v \neq u} \frac{|L_u \cap L_v|}{K}$$

High Inter-List Diversity = different users get meaningfully different recommendations. Low Inter-List Diversity = everyone gets the same top-10 popular items (popularity bias).

```python
from jurity.recommenders import DiversityRecoMetrics

# inter_list_diversity: how different are different users' recommendation lists?
inter_div = DiversityRecoMetrics.InterListDiversity(click_column='item_id', k=5,
                                                     user_id_column='user_id')

# intra_list_diversity: how diverse are items within one user's list?
intra_div = DiversityRecoMetrics.IntraListDiversity(click_column='item_id', k=5,
                                                     user_id_column='user_id',
                                                     item_features=item_embedding_df)

print(inter_div.get_score(actual, predicted))
print(intra_div.get_score(actual, predicted))
```

### Metric summary and when to use each

| Metric | Measures | Key question answered | When to prioritize |
|---|---|---|---|
| **CTR** | Click rate on shown items | "Are users clicking what we show?" | Online monitoring, business reporting |
| **AUC** | Ranking discrimination | "Can the model tell positives from negatives?" | Model selection in offline eval |
| **IPS / DR** | Unbiased CTR estimate | "What would CTR be without exposure bias?" | Policy comparison, offline A/B simulation |
| **Precision@K** | Hit rate in top-K | "Of my top-K, how many were good?" | When list length is fixed and every slot costs (ads) |
| **Recall@K** | Coverage of user interests | "Did I find the items the user cares about?" | When missing relevant items is costly (search, health) |
| **MAP@K** | Ordering quality | "Did I surface the best items earliest?" | When order within the list matters |
| **NDCG@K** | Weighted ranking quality | "How good is the full ranking?" | Standard benchmark for comparing models |
| **ILD (Intra-List)** | Variety within one list | "Does this user see diverse recommendations?" | Combating filter bubbles; session-level UX |
| **Inter-List Diversity** | Personalization across users | "Do different users get different recommendations?" | Diagnosing popularity bias; catalog health |
